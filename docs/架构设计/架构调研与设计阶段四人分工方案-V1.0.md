# 智能阅读器架构调研与设计阶段四人分工方案

- 版本：V1.0
- 日期：2026-11-11
- 状态：待小组负责人批准
- 适用阶段：架构调研与架构设计
- 适用成员：A、B、C、D
- 当前基线：V0.3 上游正式基线与 V0.4 已批准双端增量输入

## 1 文档目的

本文档用于明确智能阅读器架构调研与设计阶段的四人职责、任务边界、协作关系、阶段产出和验收条件。当前阶段聚焦架构问题定义、候选方案调研、平台架构比较、架构视图、架构决策记录和成果集成，不开展构件设计、详细接口设计、类设计、数据库表设计或正式编码实现。

四人按照以下角色开展工作：

| 成员 | 角色 | 核心责任 |
|---|---|---|
| A | 架构决策与成果集成负责人 | 管理架构基线，组织人工决策，维护 ADR，整合报告、图件和展示材料 |
| B | Windows 端架构调研与比较负责人 | 面向 Windows 11 调研候选路线、平台约束、架构策略和验证缺口 |
| C | Android 端架构调研与比较负责人 | 面向 Android 12 及以上调研候选路线、平台约束、架构策略和验证缺口 |
| D | 架构视图负责人 | 根据已确认边界和调研结果形成一致的架构上下文、逻辑、通信、部署及运行场景视图 |

### 2.3 全员共同遵守的范围

1. 文档本体、全文索引、文件授权和本地缓存保留在各端设备。
2. 云端只处理个人身份、最小同步数据、允许外发的最小证据及必要审计信息。
3. 两端同步阅读进度、笔记及最小文档身份和版本元数据，不自动同步原文件。
4. 笔记可能包含原文摘录，必须作为潜在敏感数据分析。
5. 外部 AI 调用必须经过逐文件同意、权限过滤和最少证据选择。
6. 版本变化、文件撤权或删除后，新的检索和模型使用必须被阻断，历史引用需要支持失效标记。
7. 当前性能数字仅为候选目标，未经验证不得写成正式 SLA。
8. 已有原型和实验只作为证据，不得以“已经实现”为唯一理由倒推最终架构。

### 2.4 已闭合决策的调研与验证规则

D-00 至 D-10 已经完成项目负责人决策，后续调研的目的不是重新比较并选择这些决策，而是验证其可实施性、架构影响、跨端一致性和交付风险。若验证结果与已闭合决策发生冲突，成员只能登记证据、影响和重新打开建议，不得自行修改正式结论。

验证工作分为四类：

| 类型 | 适用内容 | 验证方式 |
|---|---|---|
| 基线一致性验证 | 来源、范围、编号和版本关系 | 文档核对、追踪审查、冲突清单 |
| 架构边界验证 | 本地与云端责任、信任边界、排除范围 | 架构视图审查、数据流审计、负向检查 |
| 平台可行性验证 | 双端支持、共享核心、文件授权、离线能力和导出 | 官方资料调研、固定样本、最小工程或实验计划 |
| 交付可行性验证 | 最低系统版本、release 制品、安装和卸载 | 环境矩阵、清洁设备验证、制品检查 |

### 2.6 已闭合决策的异常处理

1. 验证通过时，在决策状态表中登记证据路径、适用环境和剩余限制，不重复创建同主题决策。
2. 验证部分通过时，优先调整候选实现、平台适配或验证范围，不自动改变产品边界。
3. 验证失败但仍存在兼容实现路径时，由 A 登记替代实现和新增实验，不重新打开原决策。
4. 验证表明决策在课程周期、平台或安全边界内不可实施时，由 A 创建重新打开建议，说明证据、影响、替代项和紧迫性，等待项目负责人批准。
5. 任何重新打开或替代决定必须形成新版本决策记录或 ADR 状态变化，旧记录继续保留。

## 3 A 架构决策与成果集成负责人

### 3.1 角色目标

A 负责维持架构工作的统一方向和可追踪性，确保 B、C 的平台调研能够使用相同评价框架，D 的架构视图能够准确表达已批准决策，并将所有成果整合为可提交、可展示和可答辩的正式材料。

### 3.2 具体任务

#### A-01 管理架构输入基线

- 登记 V0.3 正式基线、V0.4 增量输入和架构阶段新增决定。
- 维护来源编号、术语、版本和文件路径。
- 区分已批准决定、候选方案、实验事实、分析建议和未决问题。
- 检查需求模型、分析成果、技术实验与架构材料之间的冲突。
- 对无法立即关闭的冲突登记假设、风险、责任人和关闭条件。

#### A-02 组织 D-11 至 D-15 决策

- 收集 B 的 Windows 端证据、C 的 Android 端证据和 D 的候选架构视图。
- 为每项决策形成统一的候选项、评价维度、收益、代价、风险和验证缺口。
- 组织小组内部评审，但不以小组投票替代项目负责人批准。
- 记录项目负责人的最终选择、附加约束和批准日期。
- 决策改变时保留历史记录，使用“替代”或“废止”状态，不覆盖旧决定。

#### A-03 编写和维护 ADR

计划至少维护以下 ADR：

| ADR | 主题 | 主要关联决策 |
|---|---|---|
| ADR-001 | 总体架构组合与服务端粒度 | D-11 |
| ADR-002 | 共享核心与分端平台适配边界 | D-03、D-12 |
| ADR-003 | 个人进度和笔记同步冲突策略 | D-04、D-13 |
| ADR-004 | 服务端部署基线与云平台映射 | D-14 |
| ADR-005 | 外部模型网关与供应方隔离 | D-06、D-15 |

每项 ADR 至少包含背景、问题、驱动因素、候选项、决定、正面后果、负面后果、风险、状态、验证方式和关联视图。

#### A-04 统一跨端评价框架

A 需在 B、C 开始详细比较前冻结统一评价字段：

- 平台正式支持程度。
- 文档格式与复杂版面能力。
- 文件选择、授权保持和重新授权。
- 阅读、选择、搜索、bbox 与引用回跳能力。
- 本地数据、索引和安全存储适配。
- 后台任务、进程终止和状态恢复。
- 共享核心接入成本和平台桥接成本。
- release 构建、签名、安装、升级和卸载。
- 性能、内存、磁盘和开发环境成本。
- 自动化测试、调试、日志和维护能力。
- 许可证、分发和第三方依赖风险。
- 课程周期、团队技能和剩余验证成本。

#### A-05 集成正式成果

- 编写架构分析与设计报告的总论、基线、决策和结论章节。
- 合并 B、C 的平台调研结论，保留差异而非强行统一。
- 审核 D 的视图是否与正式决定一致。
- 建立报告、图件、ADR、验证证据和未决问题之间的引用关系。
- 组织课堂展示稿、答辩问题和成员讲解范围。
- 维护修改记录、版本号和提交自查清单。

### 3.4 A 的验收条件

- B、C 使用相同评价维度，结论可以横向比较。
- 每项正式架构结论都能说明需求来源或质量驱动因素。
- ADR、报告、图件和展示稿不存在相互冲突的架构边界。
- 待决策事项和待验证事项未被包装成已完成结论。
- 正式成果能够回答“为何这样设计、替代方案是什么、风险如何验证”。

## 4 B Windows 端架构调研与比较负责人

### 4.1 角色目标

B 负责研究 Windows 11 端实现智能阅读器架构目标时面临的平台能力、候选路线、约束、风险和验证缺口。B 的任务是形成架构级比较结论，而不是选择具体类库后直接进入产品实现。

### 4.2 调研范围

#### B-01 Windows 平台边界

- Windows 11 的本地文件选择、拖放、路径和文件授权恢复方式。
- 安装版与便携版对文件访问、运行时依赖和数据目录的影响。
- 多窗口、键盘鼠标、高 DPI、缩放和桌面阅读交互的架构影响。

- 凭据、令牌和本地敏感数据的安全存储能力。
- Markdown 与 PDF 导出的目标位置选择和覆盖行为。

- PDF、DOCX、Markdown 和扫描文档在 Windows 端的渲染、解析与 OCR 路线。

#### B-03 Windows 共享核心候选路线

#### B-05 Windows AI 调用与降级

## 5 C Android 端架构调研与比较负责人

### 5.1 角色目标

C 负责研究 Android 12 及以上设备实现智能阅读器架构目标时的平台能力、候选路线、限制、风险和验证缺口。由于现有技术证据主要集中在 Windows，C 需特别区分“可从 Windows 推断的共享语义”和“必须由 Android 实验验证的平台事实”。

### 5.2 调研范围

#### C-01 Android 平台边界

- 系统文件选择、Content URI、持久授权和授权失效后的重新选择流程。
- 应用沙箱对源文件、缓存、数据库、索引和导出文件的影响。
- 触摸、小屏、缩放、选区、系统返回和前后台切换的架构影响。
- 进程被系统回收、锁屏、后台限制和长任务恢复方式。
- 账号令牌、设备标识和本地敏感数据的安全存储能力。
- Markdown 与 PDF 导出时的目标位置授权和系统交互。

#### C-02 Android 文档能力路线

- PDF、DOCX、Markdown 和扫描文档在 Android 端的渲染、解析与 OCR 路线。
- 文本选择、搜索、目录导航、页码、bbox 和引用回跳能力。
- 移动设备内存、CPU、存储和功耗对解析、OCR 和索引的约束。
- 平台原生 PDF 能力、第三方组件和共享核心桥接之间的边界。
- 文档渲染结果与共享文本块、引用锚点语义的一致性风险。

#### C-03 Android 共享核心候选路线

根据 D-12 的候选范围，至少比较：

- KMP 共享核心与 Android Kotlin/Compose 平台实现。
- 共享 Rust 核心通过稳定桥接接入 Android 原生 UI 的路线。
- Qt Android 路线作为对照时的适用性、工具链和分发风险。

C 不负责直接确定最终技术栈，而是判断各路线在 Android 端需要验证的构建、桥接、生命周期、文档组件和 release 风险。

#### C-04 Android 本地优先与同步边界

- 本地文档授权、版本身份、笔记、进度、索引和缓存的持有边界。
- 离线修改进入同步队列及网络恢复后的重试行为。
- 进程回收、设备重启和后台限制对同步游标及任务状态的影响。
- 账号退出、设备丢失、令牌撤销和本地敏感数据清理。
- 文件无法重新授权或版本不一致时的 stale 和重新绑定策略。

#### C-05 Android AI 调用与降级

- 逐文件同意、最少证据外发、流式响应和用户取消的交互边界。
- 网络切换、移动网络、弱网、前后台切换和系统回收的影响。
- 在线生成不可用时保持阅读、笔记和已建索引检索可用。
- 移动端日志、崩溃信息和遥测中的隐私字段控制。

#### C-06 Android 发布与维护

- Android 12 及以上的最低版本、目标 SDK 和权限声明验证项。
- release APK 的签名、侧载、首次启动、升级覆盖和卸载验证。
- 不同 ABI、包体积、原生依赖和共享运行时的影响。
- 真机与模拟器的验证边界，避免只凭模拟器得出发布结论。
- 固定样本回归、性能测量、崩溃日志和依赖升级验证。

### 5.3 C 的评价要求

每条候选路线必须按 A 冻结的统一框架输出，并清楚标注证据等级：

- Android 已验证事实。
- Windows 证据可支持的共享语义。
- 不能由 Windows 证据推出的平台事实。
- 官方资料支持但尚未实测。
- 必须建立 Android 最小工程验证。
- 依赖 D-11 至 D-15 决策。

至少表达：

- Android 用户与 Windows 用户。

- 外部 AI 模型服务。
- 操作系统安全存储和本地数据边界。

5. 离线并发修改、同步冲突和冲突保留候选流程。
6. 文档版本变化、引用失效和重新授权。
7. 文件撤权、删除、活动任务停止和残留清理。

## 10 Git 协作与提交规则

1. 本文档在项目负责人批准前只保存在本地工作区，不提交、不推送。
2. 批准后先上传 D-00 至 D-10 决策文档和本分工方案，保证成员从 Git 获取同一工作基线。
3. 每名成员使用独立工作分支，建议命名：
   - `architecture/decision-integration`
   - `architecture/windows-research`
   - `architecture/android-research`
   - `architecture/views`
