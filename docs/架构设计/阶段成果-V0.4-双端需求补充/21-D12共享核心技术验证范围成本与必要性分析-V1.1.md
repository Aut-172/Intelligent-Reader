## 1 本次更新结论摘要

远端新增了 `experiments/android-minimal/` Android 最小工程、6 份 `TECH-ANDROID-*` 结果摘要、Android 平台调研和证据索引。该证据使 D-12 的基础发生以下变化：

1. Android 端已不再是“完全没有本地工程证据”。SAF 持久授权、WorkManager、文件队列与游标、PDF 文本与 bbox 探针、本地检索降级、侧载和卸载均已有 Android 15 真机结果摘要。
2. 已有工程验证了“纯 Kotlin 共享模块 + Android 平台适配”的职责边界，但它使用 `kotlin.jvm` 与 `kotlin.android`，没有使用 Kotlin Multiplatform 插件，因此不能写成“已验证 KMP”。
3. `shared` 模块尚未被现有 Windows 客户端实际接入；没有证明同一份共享核心在 Android 与 Windows 同时构建和运行。
4. Android 工程降低了所有选项共同承担的 Android 环境、样本、测试壳和平台适配探索成本，但 Rust/NDK/FFI 与 Qt/C++/QML 的固定启动成本基本没有下降。
5. 证据摘要中仍存在可追踪性和一致性缺口：6 份结果的 `config_hash` 为空，设备内 JSON、测试报告和 APK 未入库，证据索引部分表格仍标为“待真机”，Android 调研文档前文仍写“当前尚无 Android 实测”。
6. D-12 仍需由项目负责人选择。新证据不会自动把 A、B、C、D 或 E 中任何方案升级为最终决定。

### 2.2 新增工程结构

新增 Android 工程采用以下结构：

| 模块 | 插件/运行方式 | 主要职责 | 对 D-12 的直接含义 |
|---|---|---|---|
| `shared` | `kotlin.jvm` | 文档身份、同步模型、冲突策略、关键词索引、降级策略 | 证明纯 Kotlin 核心可以与 Android 应用按接口隔离，但尚非 KMP source set |
| `app` | `com.android.application` + `kotlin.android` | SAF、WorkManager、文件持久化、PDF 探针、结果展示 | 补齐 Android 平台适配的初步真机证据 |
| `androidTest` | Android 仪器测试 | PDF 探针、文件队列/游标恢复 | 提供设备侧可执行测试入口 |
| `results` | Markdown 摘要 | 6 项实验结论与风险 | 是结果摘要，不是完整原始证据包 |

该结构与 D-03“共享领域模型、业务规则、数据契约和可测试核心；UI 与平台适配分别实现”的方向兼容，但只能证明职责拆分可行，不能证明最终共享技术栈。

### 3.1 可以升级的判断

以下判断可从“待建立工程”升级为“已有候选证据”：

- Android 平台可以通过 SAF 而不是普通路径接入本地文档。
- Android 平台适配可以通过接口向纯 Kotlin 核心提供队列和游标存储。
- WorkManager 与持久化队列可以组合形成后台同步最小链路。
- pdfbox-android 在固定单页样本上能够产生文本、页码和字符 bbox。
- 无在线模型时，本地关键词索引可以作为降级路径。
- Android 最小工程可以在真实设备上安装、运行和卸载。

### 3.2 不能升级的判断

以下判断仍不得写成已验证：

- KMP 已在 Android 与 Windows 双端构建。
- Android 和 Windows 已运行同一份共享核心二进制或 source set。
- Android release APK 已完成正式签名、R8、升级迁移和最低版本验证。
- PDF 引用锚点已在复杂版式、版本变化和双端坐标体系下保持一致。
- D-13 A 已被正式选择。工程中的 `ConflictPolicy` 只是候选策略实现证据。
- D-15 的供应方、流式协议、外发同意和切换边界已被验证。
- 20 份文档、10 秒可读、30 秒首反馈或 60 秒完成已达到正式目标。

## 5 D-12 的研究问题如何变化

### 5.1 已部分回答

1. Android 端能否建立最小工程并接入平台文件、后台任务和本地持久化：已得到正向候选证据。
2. 领域规则和同步状态机能否与 Android UI/平台 API 隔离：`shared` 与 `app` 接口边界提供正向代码证据。
3. Android 文档组件能否输出文本和 bbox：固定单页样本上得到正向摘要。
4. Android 真机执行和侧载是否完全不可行：已被否定，基础执行链路可行。

### 5.2 仍未回答且属于 D-12 必要问题

1. 将现有 `kotlin.jvm` 共享模块迁移为真实 KMP shared module 后，Android 与 Windows 是否能稳定使用同一 source set、数据契约和测试向量。
2. 现有 Windows KMP/Compose Desktop 实验接入该共享核心时，需要多少重构和平台端口代码。
3. 同一 DocumentIdentity、同步操作和冲突结果在双端序列化后是否字节或语义一致。
4. KMP 工程能否生成 Android release-like APK 与 Windows 演示制品，并保持同一版本化契约。
5. Android 12 最低版本是否存在 API、权限、WorkManager、PDF 或签名差异。
6. 双端复杂 PDF 证据对象能否通过统一 Citation/Evidence 契约表达，而不是要求统一文档引擎。

### 5.3 不应在 D-12 重复投入的问题

除非为修复证据缺口或验证最低版本，下一轮无需从零重复：

- 再建一个仅显示页面的 Android 空壳。
- 再证明 SAF 能选择单个本地 PDF。
- 再实现一套只包含内存队列的简单同步示例。
- 再用同一个单页 PDF 证明 pdfbox-android 可以抽取文本。
- 再进行没有真实版本变化的相同 debug 覆盖安装。

下一轮应把成本集中到“双端同核、统一契约、正式构建门禁和证据可复核性”。

## 6 成本基础的变化

### 6.1 已经支付、可复用的成本

| 已有资产 | 可复用范围 | 不能被高估的边界 |
|---|---|---|
| Android Gradle 工程 | A/B/C/D/E 的 Android 最小壳、设备运行流程 | Rust/Qt 仍需各自工程和打包链 |
| Android SDK/设备执行流程 | 所有路线的真机部署与 ADB 采证 | 当前只有 Android 15 单设备摘要 |
| 固定 SELF-001 样本 | 所有路线的基础同源校验 | 单页样本不足以判断复杂文档能力 |
| SAF/WorkManager 适配经验 | KMP/Kotlin 路线可直接复用，Rust/Qt 可复用需求与测试用例 | 实现代码不一定能跨语言复用 |
| 纯 Kotlin 领域代码 | A/E 可作为迁移输入，B/C 可作为对照基准 | 目前不是 KMP 模块，也未接入 Windows |
| 结果模板和编号 | 所有路线统一证据格式 | 需补 config hash、原始日志和制品哈希 |

### 6.2 尚未支付的主要成本

| 成本 | A/KMP | B/Rust 对照 | C/Qt 对照 |
|---|---|---|---|
| 真正的双端 shared module | 仍需完成 | Rust 需另建核心 | Qt/C++ 需另建核心或明确只做组件对照 |
| Windows 接入同一核心 | 仍需完成 | 需改造 Tauri 壳调用 Rust 核心 | 需建 Qt Windows 或平台桥接 |
| Android 新工具链 | 增量较小 | NDK、Rust target、FFI/UniFFI 等仍未验证 | Qt Android kit、CMake/Ninja、NDK 仍未验证 |
| release 构建 | 真实 release 仍需补 | Rust ABI/符号/打包额外增加 | Qt 库打包、ABI、许可额外增加 |
| 调试复杂度 | Kotlin/Gradle 单栈 | Kotlin + Rust + 可能的 TypeScript/Web | Kotlin/Java + C++/QML + Qt 工具链 |
| 证据归一化 | 需补一次 | 需建立跨语言同向量 | 需建立跨框架同向量 |

### 6.3 更新后的相对剩余成本

V1.0 将“从当前零 Android 工程开始完成 A 的全部最小实验”定义为 1.0。Android 最小工程完成后，下面给出的是剩余工作量的规划区间，不是实测工时、经费或 SLA：

| 选项 | V1.0 全量成本 | V1.1 估算的剩余成本 | 变化原因 |
|---|---:|---:|---|
| A | 1.0 | 0.35–0.60 | Android 壳、平台端口和部分规则已存在；仍需真实 KMP 化、Windows 同核接入、release 与可审计证据 |
| B | 1.8–2.6 | 1.20–2.10 | 共用 Android 基础成本下降；Rust/NDK/FFI 和双端桥接成本基本未支付 |
| C | 2.0–3.0 | 1.40–2.50 | 共用 Android 基础成本下降；Qt 双端工具链、PDF 对照、许可和发布成本未支付 |
| D | 3.5–5.0 | 2.90–4.50 | 只减去共同 Android 基础；三套核心、工具链和横向分析仍是主要成本 |
| E | 初始 1.0，按门禁追加 | 初始 0.35–0.60，按门禁追加 | 阶段一由“建 Android 工程”改为“完成真实 KMP 双端门禁” |

## 7 各选项在新证据下的必要性

### 7.1 选项 A：只补齐 KMP 路线

新证据下，A 不应再定义为“再建 Android 最小工程”，而应定义为：

1. 把现有 `shared` 从 `kotlin.jvm` 迁移或重组为真正的 Kotlin Multiplatform shared module。
2. 让 Android app 与现有 Windows Compose Desktop 工程消费同一 source set 或同一版本化共享产物。
3. 双端运行同一 DocumentIdentity、同步状态机和序列化测试向量。
4. 补 Android 12、真实 release、制品哈希、测试报告和配置哈希。
5. 记录共享代码、平台端口、桥接和构建成本。

**必要性变化**：仍然高，但原因从“Android 完全没有证据”变为“已有 Kotlin/Android 原型，需要证明它能升级为真实双端共享核心”。

**成本变化**：明显下降。无需从零建立 Android 壳和平台探针，但需要处理 KMP source set、依赖可用性、Windows 工程接入和契约迁移。

**仍不能回答**：Rust FFI 或 Qt 是否提供足以抵消新增复杂度的收益。

### 7.2 选项 B：并行验证 KMP 与共享 Rust/Tauri

新证据降低了 Android 通用需求探索成本，也提供了可与 Rust 对照的 Kotlin 参考实现；但 Rust 路线本身没有新增证据。

Rust 实验仍必须至少完成：

- 与 Kotlin 版本相同的文档身份或同步状态机。
- Android 原生端到 Rust 核心的类型、错误、异步、取消和生命周期桥接。
- Windows Tauri 壳调用同一 Rust 核心，而不是继续只验证 Tauri/PDF.js。
- Android ABI、NDK、符号、崩溃和 release 打包。
- 与 Kotlin 路线相同的测试向量和证据格式。

**必要性变化**：相对下降。Kotlin/Android 路线已获得正向基础证据，因此不能再以“Android 完全未知”为理由自动启动 Rust。只有跨语言共享、性能、运行时隔离或 KMP 双端门禁出现明确阻塞时，B 的边际信息价值才高。

**成本变化**：只降低共同 Android 样本和测试设计成本，Rust 固定成本基本不变。

### 7.3 选项 C：并行验证 KMP 与 Qt

新证据证明 pdfbox-android 在单页样本上能输出 bbox，但复杂版式和双端引用坐标仍未验证。这使 Qt 的必要性变成一个更具体的问题：

> Qt PDF 是否能在复杂样本、选择、搜索、导航和引用回跳上提供明显且不可由分端组件解决的增益？

如果后续复杂样本证明 Android pdfbox-android 与 Windows PDFBox/PyMuPDF 可以通过统一 Evidence/Citation 契约归一化，Qt 的必要性进一步下降。如果复杂样本成为引用链主要阻塞，Qt 仍具有能力上限对照价值。

**必要性变化**：从“Android 文档组件完全未知”下降为“复杂文档能力条件触发”。

**成本变化**：Qt 工具链、Android kit、C++/QML、许可和分发成本没有被本次提交降低。

### 7.4 选项 D：三条路线全部验证

Android 通用基础完成不会消除三条路线的主要成本：独立核心、不同构建系统、桥接层、双端 release、错误归一化和三组两两比较仍然存在。

**必要性变化**：没有出现新的必须全验证理由。除非课程明确要求三路线实证研究，或 Rust 与 Qt 分别对应两个无法通过门禁淘汰的独立风险，D 仍是最高成本方案。

### 7.5 选项 E：分阶段门禁

E 的阶段一应更新为：

1. 不重复 Android 基础壳实验。
2. 完成真实 KMP shared module。
3. Android 与 Windows 接入同一核心并运行同一测试向量。
4. 补 Android 12、release-like、原始测试报告和配置哈希。
5. 用复杂 PDF 样本确认是否存在统一文档组件需求。

完成后，再由项目负责人根据以下触发条件决定是否追加 Rust 或 Qt：

- KMP 无法稳定完成双端同核构建。
- 共享核心被 JVM/平台依赖严重污染，端口隔离不能控制。
- 异步、性能、包体、运行时隔离或跨语言复用成为可测阻塞。
- 复杂 PDF 的 bbox、选择和引用回跳无法通过分端组件加统一契约解决。
- 仍有明确研究要求，且剩余预算足以让第二路线达到同等实验深度。

**必要性变化**：E 的初始门禁成本显著下降，且已有 Kotlin 参考实现使触发条件更容易量化；但是否采用 E 仍需项目负责人决定。

## 8 下一轮最小合格实验包

无论选择 A、B、C、D 或 E，被批准路线必须执行同一最小实验包，已完成的 Android 基础项可直接复用证据，不必重复。

### 8.1 共享核心必测

- DocumentIdentity：相同文件、改名文件、内容变化文件和错误绑定拒绝。
- 同步操作：operation id、device id、base revision、幂等、失败隔离、游标和 tombstone 数据结构。
- 序列化契约：Android 与 Windows 对同一测试向量产生语义一致结果。
- 错误契约：平台授权失效、版本不匹配、持久化失败和取消能够映射为统一错误。

### 8.2 平台端口必测

- Android：SAF URI、Android 12、进程重建、真实 release-like 构建。
- Windows：系统文件选择、本地存储、共享核心接入、演示制品构建。
- 双端：相同文档身份和同步操作不能因路径、URI 或平台时间差异错误绑定。

### 8.3 证据包必备

- 运行提交 SHA 和配置哈希。
- 测试报告、构建日志和关键 ADB/Windows 原始输出。
- APK/Windows 制品哈希、版本、签名或签名策略说明。
- 设备、系统版本、JDK/SDK/NDK/框架版本。
- 工程目录、依赖缓存、首次/清洁/增量构建时间。
- 失败样本、停止条件和未覆盖范围。

## 9 本轮不关闭的风险

1. Android 12 最低支持尚无实测，当前真机为 Android 15。
2. 只有一个设备和一个单页 PDF 样本，无法代表复杂版式和设备差异。
3. release 结论实际来自 debug APK，正式签名、R8 和严格版本升级未验证。
4. 同步只使用本地模拟，没有真实服务、弱网、乱序、时钟偏差、tombstone 和删除传播。
5. 设备内原始 JSON、测试报告、日志和 APK 未入库，结果摘要不能完全独立复核。
6. 现有共享模块不是 KMP，Windows 也没有接入同一核心。
7. 现有 `ConflictPolicy` 实现了 D-13 A 的候选语义，但 D-13 尚未由项目负责人选择。
8. Rust 和 Qt 的 Android 工具链、桥接、构建、包体和维护成本仍无新实测。
9. 当前仍缺团队可投入人数、可用日历时间、磁盘预算和停止条件的正式约束。

## 10 更新后的决策关注点

项目负责人选择 D-12 时，应基于新证据集中回答：

1. 现有纯 Kotlin Android 原型是否足以让下一轮只做真实 KMP 双端收口。
2. 在 KMP 尚未失败前，Rust FFI 仍有哪些必须通过实验回答的问题。
3. 在单页 PDF 探针已成功后，Qt 是否仍对应一个具体的复杂文档阻塞，而不是泛化的“能力可能更强”。
4. 是否要求至少两条路线的实证比较，还是允许一条路线达到完整门禁后再决定。
5. 能否接受以 V1.1 剩余成本区间作为规划输入，并另行规定最大磁盘、下载、日历时间和失败轮次。
6. 是否要求先补齐当前 Android 证据包的配置哈希、原始输出和文档状态一致性，再启动新工具链。

## 11 决策格式

现有选项保持不变：

- A：只补齐 KMP 路线的双端共享核心与正式门禁。
- B：并行验证 KMP 与共享 Rust/Tauri 路线。
- C：并行验证 KMP 与 Qt 路线。
- D：KMP、Tauri/Rust、Qt 三条路线全部验证。
- E：分阶段门禁，先完成 KMP 双端同核验证，再按预设条件申请追加 Rust 或 Qt。

建议决策记录格式：

`D-12 A/B/C/D/E；实验预算约束：______；停止条件补充：______；证据补全要求：______`

若选择 E，还需说明 Rust 和 Qt 阶段是到达门槛后自动进入，还是每次仍由项目负责人重新批准。未经明确授权，不得安装新的大型框架、启动 Rust/Qt Android 实验或扩大跨端技术验证范围。
