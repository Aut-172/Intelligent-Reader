## 1 证据等级

| 等级 | 定义 | 使用限制 |
|---|---|---|
| E1 | Android 与 Windows 正式目标直接验证，环境、样本、原始输出、复现步骤完整 | 可支持双端关闭建议，但仍需质量门槛和评审 |
| E2 | 单端正式目标直接验证 | 只能支持该平台，不能替代另一端 |
| E3 | 最小工程、局部能力或非正式目标验证 | 只能证明局部可行性，不能证明正式交付或性能门槛 |
| E4 | 官方资料、标准或供应方文档 | 证明声明和约束，不证明项目环境可行 |
| E5 | 架构分析或设计推断 | 用于形成假设、风险和实验，不作为通过证据 |
| E6 | 尚无证据 | 只能登记缺口和关闭计划 |

同一决策可以同时存在多个等级。矩阵中的“当前等级”按能够直接支持该决策关闭的最高有效范围填写，而不是按材料数量填写。

## 2 技术证据接收规则

### 2.1 必填字段

每项接收证据至少记录：

1. 实验编号与目标。
2. Git 提交、工作树或正式证据路径。
3. 操作系统、设备、SDK、运行时、依赖和版本。
4. 输入样本、授权、SHA-256 和关键版式特征。
5. 执行命令、配置哈希和原始输出路径。
6. 成功条件、失败条件和停止条件。
7. 实际结果、失败样本和已知限制。
8. 可以支持的架构结论和不能支持的结论。
9. 关联决策、ADR、质量属性场景和平台范围。
10. 是否需要复验、复验环境和关闭条件。

### 2.2 接收判定

- `Accepted Evidence`：字段完整、原始输出可复核、结论边界正确，可进入正式追踪。
- `Accepted with Limits`：可支持局部结论，但平台、样本、环境或交付范围有限。
- `Candidate Evidence`：结果存在，但未提交、路径不稳定、字段不全或尚未交叉评审。
- `Rejected as Closure Evidence`：材料可保留，但不能用于关闭当前决策。
- `Negative Evidence`：验证失败、资源超限、构建不可复现或边界冲突；必须保留并触发风险或重新打开评估。

### 2.3 禁止推导

1. Windows 证据不能替代 Android，反之亦然。
2. 单端 KMP `androidTarget + jvm` 不能证明 Android 与 Windows 正式目标双端成立；JVM target 也不能自动等同 Windows 客户端交付。
3. 一次成功构建不能证明 release、安装、升级和维护可行。
4. 单样本或最小样例不能确定 p50/p95、SLA、容量或正式预算。
5. Codex CLI、模拟适配器或合成 Evidence Contract 不能替代正式应用 API、政策、费用和限流验证。
6. 实验代码存在不能证明架构决定正确。
7. 未提交工作树不能直接成为正式证据基线。
8. 失败实验、环境阻塞、资源超限和否定结论不得删除。

## 6 当前 ADR 状态审核结论

1. D-11 至 D-35 全部维持 Proposed。
2. Android TECH 与 A-E01/02/06/10/12/13/15 可作为单端 E2/E3 证据，已提升 D-22、D-25、D-28、D-31、D-33、D-34、D-35 的 Android 侧成熟度，但不足以关闭对应双端或系统级 ADR。

4. D-19、D-27、D-29、D-30、D-32 仍无满足关闭要求的直接项目证据；D-31、D-35 只有 Android 局部直接证据，系统级证据未齐。
5. 当前没有任何 D-11 至 D-35 具备由角色 A 提出 Accepted 建议的完整条件。

## 7 实验回填流程

1. 实验负责人提交证据包或稳定路径。
2. 角色 A 按 2.1 字段完成完整性检查。
3. B/C 确认平台事实，D 确认视图影响。
4. 角色 A 更新本矩阵的证据等级、缺口和关闭条件状态。
5. 若出现否定证据，登记影响、替代实现和重新打开建议。
6. 证据完整且交叉评审通过后，角色 A 形成 ADR 状态建议。
7. 只有项目负责人批准后，更新 ADR 状态和下游报告、图件、PPT。
