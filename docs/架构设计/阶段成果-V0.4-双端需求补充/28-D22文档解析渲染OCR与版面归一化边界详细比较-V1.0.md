## 1 D-22 实际决定什么

D-22 决定的是客户端文档处理能力如何分责和归一化，而不是简单选择一个“PDF 库”。一期至少需要把以下能力放入清晰边界：

1. 文档打开与快速首屏渲染。
2. 文本抽取、字符或词级位置、段落和阅读顺序。
3. 页面坐标、bbox、选择、高亮和引用回跳。
4. 扫描页检测、OCR 触发、OCR 结果与原页图像关联。
5. 旋转、裁剪、缩放、物理页、打印页标签和坐标变换。
6. 双栏、表格、公式、脚注、页眉页脚和异常字体的降级语义。
7. 解析结果缓存、版本、失效、重建和异步生命周期。
8. Android 与 Windows 在组件能力不一致时如何保持统一证据合同。

D-22 不负责决定本地索引算法、RAG 分割、最终引用锚点结构、KMP 最终采用或性能正式 SLA。这些分别留给 D-23、D-24、D-25、D-28 和 D-33。但 D-22 必须向这些决策提供稳定的文档中间表示和能力降级信号。

## 2 不可绕过的既有边界

### 2.1 本地数据边界

- 文档本体、页面图像、解析结果、OCR 结果和全文索引留在客户端。
- 服务端和外部模型不得为了简化解析而默认接收完整文档。
- 因此“统一上传到服务端解析”不能作为普通 D-22 选项；若要采用，必须重新提交数据边界和外发同意决策。

### 2.2 双端与共享核心边界

- Android 12+ 与 Windows 11 都必须形成正式证据。
- 共享核心复用文档合同、坐标语义、状态机和测试向量，不等于两端必须使用同一个原生库。
- UI、文件授权、渲染表面、系统选择和平台安全存储继续分端实现。

### 2.3 证据与引用边界

- 一个可检索文本块若不能稳定回到 `DocumentVersion + physicalPage + bbox/结构锚点`，只能降级为页级或章节级引用，不能伪装成精确高亮。
- OCR、表格和复杂版面的低置信度必须传播到检索、回答和引用层。
- 文档版本或解析配置变化后，旧锚点必须可识别为 stale，而不是错误跳转。

### 2.4 生命周期边界

- 渲染、文本抽取、OCR、结构分析、索引和缩略图不应被建模为一个同步阻塞步骤。
- 一期候选目标仍只是“10 秒可读、30 秒首反馈、60 秒完成”等待验证值，不能作为已承诺 SLA。
- 文档必须允许先进入可读状态，再异步补齐抽取、OCR、结构和索引。

## 3 当前已有证据及其边界

### 3.1 Android PDF 证据

`experiments/android-minimal` 已固定 `pdfbox-android 2.0.27.0`。`TECH-ANDROID-003-R01` 在自制单页 PDF 上证明：

- Android 能抽取文本块、页码和有限非负 bbox；
- 三个中文锚点可命中；
- 简单页面阅读顺序自上而下成立；
- 源文件 SHA-256 与桌面样本一致。

该证据不能外推到：双栏、表格、公式、扫描页、复杂字体、多页性能、交互式渲染、文本选择或真实高亮 IoU。Android 抽取为 17 个块，桌面 PyMuPDF 基线为 10 个块，已经表明两端块粒度并不天然一致。

### 3.2 Windows/桌面解析证据

`experiments/parser-benchmark` 已保存 PyMuPDF、pdfplumber、Docling、Unstructured、Apache Tika 等候选结果。当前证据支持：

- PyMuPDF 可提供页面、文本块/词、bbox 和渲染坐标的局部基线；
- 通用文档框架可输出更丰富结构，但依赖、模型、性能和失败模式明显更复杂；
- 阅读顺序、标题层级、段落边界和表格网格不能只用关键词命中替代人工金标；
- 实验环境中的 Python 工具可作为能力和金标证据，不等于已经适合嵌入 Windows 正式客户端。

### 3.3 OCR 证据

既有 OCR 结果表明：

- Tesseract、RapidOCR 和 PaddleOCR 路线均形成了局部可运行证据；
- RapidOCR 可返回行级 polygon bbox，清晰自制样本表现较好；
- 公开样本中 RapidOCR/Tesseract 固定问题通过率明显下降，180 度页面和表格行关系失败；
- PP-StructureV3 可输出复杂布局和表格单元格，但 CPU 时延与稳定性目前只适合作为异步增强实验，不适合一期同步主路径；
- OCR 高置信度不等价于结构正确或精确引用可靠。

因此 D-22 必须区分“可读/可搜索的最佳努力 OCR”和“可用于精确回答及 bbox 引用的可信 OCR”。

### 3.4 引用与坐标证据

`TECH-CIT-004-R01` 已证明现有 OCR 词框和 PDF IR bbox 可以转换到统一的顶部左原点坐标语义并保持边界有效；但没有人工词级高亮金标，不能宣称实际高亮 IoU 已通过。`TECH-CIT-009-R01` 也支持 PDF/扫描文档使用 `page_bbox` 路由、无视觉页格式使用 `section_paragraph` 路由，并要求不可用时显式降级。

### 3.5 证据结论

当前证据足以证明“统一合同 + 多种适配器”在概念上可行，也证明组件差异真实存在；不足以证明 A、B 或 C 中任何一个已经满足双端正式交付。D-22 的决定仍需项目负责人基于范围、成本和风险选择。

## 4 共同文档合同：无论选择哪一项都需要

D-22 的选项决定组件组织方式，但下列合同应作为候选共同基线，字段是否正式冻结留给 D-25：

| 合同对象 | 最小语义 | 不应包含 |
|---|---|---|
| `DocumentSource` | 本地授权引用、格式、大小、内容哈希、版本 | 可跨设备复用的本地路径或 URI |
| `DocumentPage` | physical page、可选 printed label、尺寸、旋转、裁剪框 | 依赖某一 UI 控件的对象 |
| `DocumentElement` | element id、类型、文本、阅读顺序、页码、bbox、字符范围、置信度 | 组件私有对象或不稳定内存地址 |
| `TextSpan` | 文本、页内坐标、源元素、语言和 OCR 标记 | 未说明坐标系的裸 bbox |
| `PageTransform` | 文档点、归一化坐标、渲染像素之间的变换 | 隐含缩放或旋转假设 |
| `ParseArtifact` | parser id/version/config、source hash、生成时间、能力集 | 无版本的长期缓存 |
| `CapabilityStatus` | render、text、selection、bbox、OCR、structure 的 available/degraded/unavailable | 用空值冒充成功 |
| `DocumentIssue` | 低置信度、双栏风险、表格风险、字体错误、旋转失败 | 只写日志而不进入业务降级的信息 |

坐标建议至少明确：原点、单位、页面旋转前后、裁剪框、缩放和 bbox 形态。组件原始坐标不得直接泄漏到引用合同。

## 5 选项 A：平台原生或平台成熟组件 + 统一文档能力契约

### 5.1 方案定义

Android 和 Windows 各自选用适合本平台的成熟渲染/抽取能力，通过统一合同输出页面、文本、bbox、阅读顺序和能力状态。两端不要求使用同一底层引擎，但必须使用同一金标样本、坐标语义、错误分类和降级规则。

该方案中的“平台组件”可以是操作系统能力，也可以是易于嵌入该平台的成熟库；D-22 A 不等于现在就正式选择 PDFBox-Android 或 PyMuPDF。

### 5.2 收益

- 能直接利用各平台文件、渲染、线程和内存管理能力，首屏与交互集成路径较短。
- 与 D-03 的共享合同、分端 UI 最自然兼容。
- Android 已有 PDFBox 局部证据，实验起点最低；Windows 可复用现有解析金标而不必立即引入跨平台原生工具链。
- 单个平台组件失败时可在该平台局部替换，不必同步升级另一端二进制。
- 适合把“可读渲染”与“后台抽取/OCR”拆成不同生命周期。

### 5.3 可行性

总体可行性高。简单文本型 PDF 的渲染、抽取、页码和 bbox 已有局部证据。主要不确定性不是能否打开 PDF，而是两端不同组件如何产生可比较的阅读顺序、块粒度和高亮坐标。

### 5.4 实施难度

中。平台集成难度相对可控，但统一合同和差异治理不能省略。若只抽象一个 `extractText()` 接口，会把组件差异推迟到引用、索引和 UI 阶段，形成隐蔽缺陷。

### 5.5 技术需求

- 每端一个渲染适配器和一个解析/OCR编排适配器，二者允许底层组件不同。
- 统一坐标与页面模型、解析配置版本和能力矩阵。
- 固定 PDF 样本：单栏、多页、双栏、表格、旋转、异常字体、图片扫描、混合文本层。
- 统一金标：物理页、阅读顺序、关键文本、bbox、高亮区域和降级期望。
- Android/Windows 各自产出同格式 IR，再进行差异报告；不能要求块 ID 或块数量完全一致，但证据锚点必须等价可回跳。

### 5.6 与现有决策兼容性

- 与 D-12 A 高度兼容：KMP 可共享合同、状态机和测试向量，平台适配器分别实现。
- 与 D-20 A 兼容：缓存和解析产物按平台目录实现，但共享生命周期语义。
- 与 D-05 A 兼容：全部在客户端处理。
- 与 D-25 的引用锚点设计兼容，但会增加“能力差异与降级”字段。

### 5.7 风险及验证

- 风险：同一文档在两端的分块和阅读顺序不同，笔记或引用不能稳定恢复。
- 风险：渲染引擎与抽取引擎坐标不一致，bbox 看似有效但高亮错位。
- 风险：某平台组件对中文字体、旋转、表格或扫描页支持明显弱于另一端。
- 验证：同源文件、同一关键证据的跨端页面定位和人工高亮 IoU；旋转/缩放/裁剪变换；块粒度差异下的稳定锚点；组件升级回归。

### 5.8 实验成本与必要性

- 成本：低到中。可以在现有 Android 最小工程和 Windows 既有解析样本上补齐合同输出，不需要立即安装新的大型跨平台框架。
- 必要实验：必须做双端同源 PDF 金标比对、真实渲染高亮、双栏/旋转/扫描页降级；否则 A 的主要风险没有被验证。
- 可延后实验：大规模 OCR 引擎排名、复杂表格结构化和全部格式覆盖可在一期范围冻结后按需进行。

## 6 选项 B：跨平台文档引擎统一承担核心文档能力

### 6.1 方案定义

Android 与 Windows 嵌入同一跨平台文档引擎或同一核心实现，由它统一负责 PDF 渲染、文本抽取、页面坐标、选择和基础阅读顺序；平台层只负责文件授权、窗口/画布、输入和系统集成。OCR 可以作为同一引擎的扩展或受统一编排的外部模块。

候选形态可能包括可跨平台嵌入的 C/C++ 文档引擎及其绑定，但 D-22 B 不等于选择 Qt，也不等于重新打开 D-12 的三路线并行验证。

### 6.2 收益

- 两端更容易获得一致的页面几何、选择、bbox 和渲染行为。
- 解析配置、错误修复和回归测试可以围绕一套引擎集中维护。
- D-25 引用锚点与坐标回跳的跨端差异理论上更小。
- 对复杂 PDF 特性，专业文档引擎可能比平台通用组件提供更完整能力。

### 6.3 可行性

技术可行性中到高，但项目可行性取决于许可、Android ABI、Windows 打包、包体、原生崩溃诊断和绑定质量。当前仓库尚没有同一引擎的 Android/Windows正式嵌入证据。

### 6.4 实施难度

高。需要管理原生二进制、多个 ABI、构建缓存、符号、线程模型、内存生命周期和升级。即使引擎统一，OCR、结构分析和 UI 选择仍可能需要额外适配，不能假设“一套引擎解决全部文档问题”。

### 6.5 技术需求

- 明确许可和分发条件，包括静态/动态链接、商业限制和第三方声明。
- Android arm64/x86_64 与 Windows x64 构建、签名、崩溃符号和自动化测试。
- Kotlin/Java 与原生引擎绑定，Windows UI 与原生渲染表面集成。
- 统一线程、取消、资源回收、密码 PDF、损坏文件和超大页面防护。
- OCR 与结构分析的扩展边界，避免把重量级模型塞入首屏主路径。

### 6.6 与现有决策兼容性

- 与 D-03 兼容，但共享范围会从领域核心扩大到原生文档核心，需要项目负责人明确接受验证范围变化。
- 与 D-12 A 存在实验预算张力：若 B 需要新的大型工具链或 Qt/Rust 并行工程，必须另行授权，不能由 D-22 自动启动。
- 与 D-08 的 APK 和 Windows 演示包兼容，但会增加包体、构建和分发风险。

### 6.7 风险及验证

- 风险：统一引擎形成单点技术和许可依赖，一次升级同时影响两端。
- 风险：原生崩溃或内存问题跨越 KMP/平台调试边界，课程团队定位成本高。
- 风险：引擎统一页面几何，但并不自动统一 OCR、结构和语义分块。
- 验证：最小双端嵌入、相同样本渲染/抽取一致性、包体和构建时间、内存压力、原生崩溃诊断、离线安装和许可清单。

### 6.8 实验成本与必要性

- 成本：高。至少需要一套新的双端原生构建、绑定和打包链路；若候选依赖 Qt 或其他大型 SDK，磁盘和学习成本进一步提高。
- 必要实验：只有在跨端 bbox/选择一致性被认定为不可妥协，且 A 的金标差异无法通过合同归一化控制时，B 的双端嵌入实验才具有高必要性。
- 停止条件：许可不适合分发、Android ABI/包体不可接受、Windows 集成不稳定、原生崩溃不可诊断，或简单样本一致但复杂样本仍依赖外部多引擎时，应停止扩大验证。

## 7 选项 C：按格式与平台组合组件，通过规范化适配层统一

### 7.1 方案定义

根据文档格式、页面类型和能力需求选择不同组件。例如：PDF 用专用渲染/抽取器，扫描页进入 OCR，Markdown 用结构解析器；复杂表格或布局只在异步增强路径调用重量级组件。所有结果经规范化适配层合并为统一文档模型。

C 与 A 的区别是：A 倾向每个平台维护一个主要文档能力栈；C 明确接受同一平台、同一文档生命周期内存在多个组件和能力路由，并把路由、合并、置信度与回退作为正式架构责任。

### 7.2 收益

- 能针对不同格式和风险选择效果更好的组件，避免最低公分母限制。
- 可把快速渲染、轻量抽取和重量 OCR/结构分析分层，兼顾首屏与增强质量。
- 与现有多引擎实验最贴近，可复用 PyMuPDF、OCR 和结构分析的比较证据。
- 单个组件失败时可以降级或转入替代适配器。

### 7.3 可行性

总体可行性中到高。当前实验已证明多种产物可以被转为相近 IR，但尚未证明在 Android 与 Windows 正式客户端内的组件路由、资源预算和一致性。

### 7.4 实施难度

高。主要复杂度不在单个库，而在能力探测、任务编排、结果合并、冲突选择、缓存版本和错误解释。若没有严格合同，C 容易演变为“每个组件输出一套数据”。

### 7.5 技术需求

- `DocumentCapabilityRouter`：根据格式、文本层、页面复杂度、设备资源和用户设置选择处理路径。
- 规范化 IR 与 provenance：每个元素记录来源组件、版本、配置、置信度和变换链。
- 多阶段状态：render-ready、text-ready、ocr-pending、structure-enhanced、degraded、failed。
- 合并规则：原生文本层与 OCR 重叠时如何去重；表格/标题增强如何关联原始页面；组件结论冲突时谁优先。
- 资源预算与取消：限制并发、CPU、内存、临时空间和后台任务时长。

### 7.6 与现有决策兼容性

- 与 D-06 的端侧非生成式能力研究兼容，但重量模型不能被误写为一期必需能力。
- 与 D-12 A 兼容程度中等：合同和状态机可由 KMP 共享，具体组件仍分端；若 Android 需要新增多个大型模型或原生工具链，则必须另行批准实验范围。
- 与 D-20 A 高度相关，需要为多个缓存和产物建立清理、迁移和容量策略。
- 对 D-25 最灵活，但 provenance 和置信度字段会更复杂。

### 7.7 风险及验证

- 风险：不同组件产生重复或冲突文本，检索和引用指向错误来源。
- 风险：异步增强改变阅读顺序或 element id，使已有笔记和引用变 stale。
- 风险：大量依赖增加安装、包体、漏洞、许可和升级成本。
- 风险：路由在两端不同，导致相同文档进入不同能力等级。
- 验证：同页多引擎合并、文本层+OCR去重、增强前后锚点迁移、资源限额、取消恢复、组件缺失和低端设备降级。

### 7.8 实验成本与必要性

- 成本：中到高。可以先复用桌面既有结果验证路由与IR，不必立刻把全部组件嵌入客户端；但正式证明仍需 Android/Windows 最小集成。
- 必要实验：若一期明确包含扫描 PDF，至少需要“文本层检测→OCR→页级/bbox级降级”的端到端路径；若只承诺文本型 PDF，则复杂结构引擎实验可延后。
- 控制方法：先冻结一期格式和能力分级，只验证必需路径；每新增组件必须说明它关闭了哪个金标缺口，否则不进入正式依赖。

## 8 三项方案对比

| 维度 | A 平台组件+统一契约 | B 跨平台文档引擎 | C 格式/平台组合组件 |
|---|---|---|---|
| 首轮实验成本 | 低到中 | 高 | 中到高 |
| 正式集成成本 | 中 | 高 | 高 |
| 跨端页面几何一致性 | 中，依赖归一化 | 高，限于同引擎能力 | 中，依赖路由与合并 |
| 复杂格式上限 | 中 | 中到高 | 高 |
| 首屏与异步分层 | 容易 | 中 | 最灵活 |
| 依赖/许可数量 | 少到中 | 少但单体较重 | 多 |
| 原生工具链风险 | 低到中 | 高 | 中到高 |
| 与 D-12 A 兼容 | 高 | 中，可能需扩实验 | 中到高 |
| 替换单个组件 | 中 | 低到中 | 高，但合同复杂 |
| 最主要风险 | 两端差异破坏引用 | 单引擎与原生集成锁定 | 编排和结果合并失控 |

## 9 实验成本与必要性的判断框架

### 9.1 先回答范围，避免无效实验

在选 D-22 前，应至少明确一期文档范围的最低表达：

- 是否只有 PDF，还是还包括 Markdown/TXT/DOCX；
- PDF 是否正式承诺扫描件；
- 扫描件是“可读和最佳努力搜索”，还是承诺精确问答和 bbox 引用；
- 表格、公式、倒置页和印章是否属于正式能力、最佳努力或明确不支持；
- 引用最低要求是页级、段落级还是可视 bbox 高亮。

若这些范围不明确，任何组件对比都会把不同能力混成一个“支持 PDF”的结论。

### 9.2 最低必要实验包

无论选择 A、B 或 C，都建议把下一轮证据限制为一个可控包，不安装无关大型框架：

1. 选取 6 至 10 份固定、可授权、可重放的 PDF：简单单栏、多页、双栏、表格、旋转、异常字体、扫描、混合文本层。
2. Android 与 Windows 对同源 SHA-256 文件输出统一 IR。
3. 人工标注少量关键证据的物理页、阅读顺序和高亮矩形。
4. 检查首屏渲染与后台解析能否解耦，不把候选时限写成 SLA。
5. 记录组件版本、配置、耗时、峰值内存、产物大小、失败和降级状态。
6. 验证引用从 IR 回到真实渲染页面，而不是只检查 bbox 数值非负。

这个实验包是 D-22 的最低必要证据，因为当前最大缺口正是双端真实高亮和复杂样本一致性。

### 9.3 不应立即投入的实验

- 不应为了“比较完整”同时安装 Qt、另一套跨平台原生引擎和多个 Android OCR 模型。
- 不应在一期格式未冻结前对所有办公格式做全量解析排名。
- 不应把桌面 Python 基准直接包装成正式 Windows 客户端服务而跳过分发、资源和安全评估。
- 不应把高置信度 OCR 或关键词命中当成阅读顺序、表格结构或引用高亮通过。

### 9.4 触发扩大实验的条件

只有出现以下证据时才建议扩大成本：

- A 的平台组件在核心样本上无法产生可归一化的页码/bbox，且直接破坏 D-25 引用目标；
- 扫描 PDF 被正式纳入一期，现有轻量 OCR 路径无法达到已批准的最低能力等级；
- 同一组件在 Android 或 Windows 存在不可修复的许可、稳定性、包体或性能问题；
- C 的路由确实能关闭一个已量化缺口，而不是只增加候选组件数量。

## 10 对 D-22 选择的解释边界

### 10.1 若选择 A

表示正式采用“分端组件、统一合同和金标”的责任模式。它不等于确认 PDFBox-Android、PyMuPDF 或某个 Windows 组件为最终库；具体组件仍需验证和后续技术清单确认。

### 10.2 若选择 B

表示愿意把同一文档引擎的双端嵌入、许可、原生构建和分发纳入验证范围。若该验证超出 D-12 A 的现有预算，应另行批准实验范围，而不能自动开始。

### 10.3 若选择 C

表示正式接受能力路由、多个解析产物、provenance 和合并规则作为架构责任。它不代表所有实验组件都进入一期产品依赖。

### 10.4 三项都不自动确定

- 一期支持的格式清单和扫描件承诺等级；
- OCR 具体引擎与模型；
- D-25 的最终锚点字段；
- D-33 的性能、内存、容量和准确率阈值；
- D-28 的最终共享核心技术栈。

## 12 当前需要项目负责人选择

请从责任模式角度选择，而不是把选项字母理解为具体库：

`D-22 A / B / C`

- A：平台原生或平台成熟组件 + 统一文档能力契约。
- B：跨平台文档引擎统一承担核心文档能力。
- C：按格式与平台组合组件，通过规范化适配层统一。

如需附加一期范围，可同时说明是否正式支持扫描 PDF，以及引用最低要求是页级还是 bbox 高亮；未说明时，这两项继续保持研究问题，不由本文件代选。
