# 智能阅读器：相近产品与成熟系统架构案例调研

- 版本：V1.0；核查日期：2026-11-25
- 定位：补充 `35-软件架构调研分析报告-V1.1.md` 的具体系统案例，不替代双端实验或 ADR 评审。
- 证据标记：**事实**仅指官方文档可核验内容；**借鉴**是本项目推论；**未知**不从功能表象倒推内部实现或性能。

## 1 范围与方法

需求阶段的 `同类阅读器分析.pdf` 已比较 ChatDOC、Kimi、MarginNote、Zotero、Readwise Reader、WPS Office AI。“产品形态”或界面表现不等于内部模块、数据流、同步协议和部署边界的证据。本稿选择官方技术资料可核验局部机制的 Zotero、Obsidian，以及作为成熟大规模系统机制参照的 GitLab、OpenSearch。后两者不是同类阅读器；案例公开信息不能代替项目自己的双端实验。

比较问题：数据在哪里、离线与同步如何分界、模块和部署如何组织、扩展点与任务如何治理、质量属性的收益和代价是什么。分别映射需求用例、逻辑架构和 ADR；映射属于本项目论证，不是案例系统与本系统架构等同的声明。未获得公开架构证据的竞品不臆测内部实现。

## 2 Zotero：本地文献库与分开的同步通道

**事实。** 数据目录含 `zotero.sqlite` 和附件目录 [Z1]；官方区分库数据同步与附件文件同步，前者包含条目、笔记和标签等，后者可以使用 Zotero Storage 或 WebDAV [Z2]。这不等于“仅同步元数据”：偏好设置允许同步 PDF 等附件的已抽取全文内容 [Z3]。官方警告不可将活动数据库直接置于普通云盘同步目录，避免损坏 [Z4]。Zotero 7 开发资料描述插件 manifest、生命周期与阅读器扩展接口 [Z5]；插件有访问库和本机的权限风险 [Z6]。

**借鉴。** 本地数据可用、不同数据类型有独立同步策略、冲突显式处理、稳定核心配置可替换扩展，适合作为离线优先及局部微内核式扩展机制参照。UC01/02/04/09/10/12 对应本地文档/笔记和结构化同步；ADR-013/017/019/020/021 对应冲突副本、最小同步与删除传播；ADR-022 对应解析组件合同。本项目**不照搬附件及全文同步**：原文、解析结果和索引留端，只上传最小结构化状态；一期也不开放任意第三方插件。

**未知。** 上述资料不证明 Zotero 的服务端是微服务、使用本项目 revision/cursor 协议，或在特定负载下的性能。

## 3 Obsidian：本地 vault 与受控扩展

**事实。** 笔记是本地 vault 中的 Markdown 文件，外部文件变更可刷新；设置放在 `.obsidian` 目录 [O1]。官方说明本地笔记可离线使用，跨设备同步有 Obsidian Sync 等选项 [O2]。插件开发资料规定插件结构、manifest 与 API，并建议在独立测试 vault 中开发以免损坏真实笔记 [O3]。

**借鉴。** 本地源数据与可重建派生索引分离，提升弱网可用性；插件 API 体现局部扩展点，但不能断言整个产品严格采用微内核架构。UC01/04/05/09 与 ADR-020/022/023/033 对应本地存储和索引生命周期。本项目处理 PDF/DOCX/EPUB、OCR、版本化引用和按次外发授权，不能直接复制 Markdown 文件同步或通用插件市场；采用受控 Parser/ModelAdapter 合同。

**未知。** 资料不能证明其服务端同步算法、内部完整层次、缓存失效细节或大规模部署拓扑。

## 4 GitLab：大规模组件边界和渐进部署

**事实。** GitLab 的“至多 1,000 RPS 或 50,000 用户”参考架构列出负载均衡、Web/API、Sidekiq、PostgreSQL、Redis、Gitaly 等组件和节点组 [G1]；其扩展文档说明 Web/API 与 Sidekiq 对 PostgreSQL 的依赖 [G2]。后台任务有 Sidekiq worker 的队列、幂等和资源治理规范 [G3]。这是一个部署规模的参考拓扑，**不能概括为每个业务能力都是独立微服务**。

**借鉴。** 交互请求、后台任务和持久数据资源特征不同，负载增长后可分开配置；更多节点、缓存与队列也增加运维及故障面。UC12 与 ADR-011/026/030/032/035 对应身份同步、AI/RAG 网关、任务审计 Worker 的逻辑责任。本项目一期允许同机部署，以 PostgreSQL 任务表、lease 和幂等恢复长任务；不因 GitLab 使用 Sidekiq/Redis 而默认引入消息中间件。仅在容量、故障隔离或发布独立性出现实证时重评拆分。

**未知。** GitLab 参考负载不是本系统性能预算，不可推导我们的数据库瓶颈或部署时机。

## 5 OpenSearch：索引环节的管道-过滤器机制

**事实。** Ingest pipeline 是有序处理器序列，每阶段消费上阶段输出，索引前过滤、转换或增强文档；它在 OpenSearch 集群节点运行，而 Data Prepper 是集群外的独立服务 [S1]。官方提供阶段或管道级失败处理 [S2]，以及不实际写索引的样本模拟 API [S3]。

**借鉴。** 清楚的阶段输入输出、失败策略和样本回归适合客户端“授权读取→解析/OCR→规范化→切分/索引→检索/证据筛选→引用核验”。UC01/02/05/06/08 与 ADR-016/022/023/024/025/033/034 对应端侧管道和双端金标。各阶段保留 DocumentVersion、ParserVersion、来源、置信度和降级原因。**只借处理器模式，不采用集群或云端全文索引**；管道也不能代替阅读交互、同步事务与权限决策。

**未知。** 服务端 ingest 处理器的吞吐不等于 Android/Windows OCR 和嵌入性能。

## 6 按课程质量维度权衡

以下是**本项目适配性判断**，不是案例系统的实测评分；大规模系统机制只取其有用的局部。

| 维度 | 案例揭示的收益与代价 | 本项目选择/验证条件 |
|---|---|---|
| 性能 | 本地访问省网络往返，重处理占端侧资源；后台工作可独立隔离 | 本地检索；测双端建索引时延、内存及 AI 首反馈 |
| 可扩展性 | 插件和处理阶段可替换，但接口、版本和信任治理昂贵 | 受控解析器与模型适配器，不开放任意插件 |
| 可用性 | 本地阅读不依赖云；任务与同步需恢复机制 | 离线阅读/笔记；AI/SSE 中断后查询最终结果降级 |
| 安全性/可信性 | 插件权限和同步范围可能扩大内容暴露；管道元数据利于溯源 | 按次同意、最少证据外发、双锚点引用和保守 stale |
| 部署复杂度 | 多节点/中间件有故障隔离收益，也增加维护成本 | 三个粗粒度逻辑单元可同机；无默认事件总线 |
| 可伸缩性 | 后台单元可按负载扩容；端侧受设备预算限制 | 先测容量、争用和恢复，再决定物理拆分 |
| 可测试性 | 固定样本与处理器模拟便于回归；分布式链路更难测 | 双端文档金标、同步幂等与网络外发测试 |
| 可观测性 | 阶段/队列错误便于定位，但日志易泄露内容 | 内容无关遥测、任务状态与明确降级原因 |

**选型结论。** 客户端采用分层、本地优先，文档处理采用端侧局部管道与受控适配点；服务端保留少量粗粒度逻辑单元。普通通信 REST/JSON，AI 用 SSE 并以最终结果轮询降级；长任务持久化但一期不默认引入 Kafka、RabbitMQ 或独立事件总线。RAG 分工为“本地检索与筛选→最少证据外发→云端生成→客户端引用核验”。案例论证不会将 Proposed ADR 自动改为 Accepted，也不能替代既有实验门槛。

## 8 后续实证和答辩边界

1. 用 Android 12+、Windows 11 固定样本测解析/OCR/索引资源、引用准确率和降级；产品案例不代替双端证据。
2. 用真实后端测试 SyncOperation 幂等、revision/cursor、tombstone、长离线及冲突副本；案例同步功能不证明本项目协议正确。
3. 用正式模型 API 核查最少证据外发、限流、费用、SSE 中断及轮询恢复；上述案例不证明本项目 RAG 质量。
4. 答辩时明确区分“官方事实—本项目推论—未知/待验证”，不把 GitLab 大规模拓扑或 OpenSearch 集群索引画成本项目一期部署。
