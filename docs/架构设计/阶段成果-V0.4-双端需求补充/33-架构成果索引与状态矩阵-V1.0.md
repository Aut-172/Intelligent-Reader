## 1 状态与来源规则

### 1.1 来源优先级

1. 正式目录中的最高版本文件是决策、范围和状态的权威来源。
2. `docs/架构设计/阶段成果-V0.4-双端需求补充` 是正式文件的 Git 协作副本；副本内容必须与正式目录一致。
3. `docs/架构设计` 下的平台调研、证据索引和图件是成员协作输入，需经角色 A 接收和交叉评审后进入正式成果。
4. `experiments` 下的代码、结果和工作树是技术证据，不等于架构结论。
5. `2组架构调研与设计`、`_incoming`、`.tmp` 和未跟踪并行稿只作历史、差异或待接收输入。

### 1.2 状态词典

| 状态 | 含义 |
|---|---|
| Accepted | 已由项目负责人批准且当前无待关闭的架构决策条件 |
| Selected / Proposed | 方向已选，但 ADR、参数、实验或一致性评审未关闭 |
| Draft | 已形成可评审稿，尚未完成交叉评审 |
| Active | 持续维护的治理文件 |
| Waiting Input | 等待其他角色或实验输入 |
| Historical | 保留历史，不作为当前权威结论 |
| Superseded | 已由更高版本替代，但不得删除 |
| Candidate Evidence | 可供接收的候选证据，尚未进入正式证据基线 |

## 7 维护规则

1. 新文件或新版本产生后，先更新本索引，再更新下游报告引用。
2. 历史版本只标记 Superseded 或 Historical，不删除、不覆盖。
3. 实验结果必须先进入 34 的证据追踪，再用于 35、36 或 ADR 状态建议。
4. 任何 ADR 转 Accepted 必须有项目负责人批准记录；角色 A 只提出建议。
5. 角色 D 图件必须标明 Proposed、Candidate 或 Accepted；当前不得出现“最终部署图”。
6. 正式目录和 Git 副本同步后应核对 SHA-256；不以文件名相同代替内容一致。
7. Office 文件只在 Markdown 内容稳定并完成交叉评审后集中生成或更新。
