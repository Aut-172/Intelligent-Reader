# D-21 同步协议与客户端状态机详细比较

- 版本：V1.0
- 日期：2026-11-17
- 状态：Decision Input / Research Question
- 前置选择：D-13 A、D-16 A、D-17 A、D-18 A、D-19 A、D-20 A
- 决策人：当前对话人

## 1 D-21 实际决定什么

D-21 决定的不是某一个接口路径，而是离线修改如何成为可信服务端状态，以及客户端如何证明自己没有漏掉远程变更。它至少包含六个相互依赖的问题：

1. 客户端上传“操作”还是上传“资源最终状态”。
2. 服务端使用全局变更序号、资源 revision，还是不可变事件日志表达顺序。
3. 上传、生成远程变更和返回结果是否位于同一事务边界。
4. 客户端何时删除本地离线操作，何时推进拉取游标。
5. tombstone 过期、游标失效和旧设备重连时如何重新建立基线。
6. 旧客户端、协议版本和字段迁移如何保持兼容或被明确拒绝。

D-21 不负责决定：公共 AI 流式协议、服务间 RPC、具体数据库或消息中间件。这些分别留给 D-27 和 D-30。但 D-21 会给它们提出必要能力。

## 2 前置决策带来的协议约束

### 2.1 D-13 A

- 笔记并发编辑必须产生冲突副本，不能静默最后写入覆盖。
- 阅读进度只在相同 DocumentVersion 下按服务端可信顺序比较。
- 删除使用 tombstone，旧设备不得用删除前 revision 复活数据。

### 2.2 D-16 A

- 同步载荷必须同时携带 DocumentIdentity 和精确 DocumentVersion。
- 内容哈希变化而未建立显式版本关系时，进度、笔记和引用保持独立。
- 服务端不能根据文件名或路径自动绑定文档。

### 2.3 D-17 A

- 服务端可以处理结构化进度、笔记正文、冲突副本和受限短摘录。
- 协议必须执行字段和长度限制，并避免原文进入错误响应或日志。

### 2.4 D-18 A

- 每个同步请求必须关联账号、设备会话和随机 device ID。
- 设备撤销后，旧令牌和旧设备上传必须被拒绝。

### 2.5 D-19 A

- tombstone 有固定短期保留期，但具体天数未确定。
- tombstone 清理后，长期离线设备不能继续基于旧游标上传；需要游标失效或数据世代门禁。

### 2.6 D-20 A

- 客户端队列和游标必须持久化，但一期主要依赖平台数据保护，不假设整个队列端到端加密。
- 错误日志不得输出笔记正文、摘录、令牌或本地路径。

## 3 所有方案必须满足的公共不变量

1. **幂等不变量**：同一账号下重复提交相同 `operationId`，业务效果至多发生一次，返回结果保持兼容。
2. **版本不变量**：任何更新携带 `baseRevision`；过期写入必须进入冲突、删除拒绝或显式重试，不能静默成功。
3. **删除不变量**：服务器已存在更高删除 revision 或 tombstone 时，旧 upsert 不得复活对象。
4. **游标不变量**：客户端只有在远程变更全部持久化或原子提交后才能推进游标。
5. **队列不变量**：客户端只有取得确定的成功或终态拒绝结果后才能移除本地操作；网络超时不能推断失败。
6. **设备不变量**：设备撤销和令牌失效必须先于业务写入判定。
7. **文档版本不变量**：跨 DocumentVersion 的进度不得自动合并；笔记锚点迁移不得由同步协议猜测。
8. **隐私不变量**：接口错误、日志、指标和追踪不包含笔记正文与原文摘录。
9. **有界不变量**：上传和拉取均有批次、大小、时间和重试上限。
10. **兼容不变量**：服务端必须识别协议版本，不能让未知字段或旧语义悄悄破坏新数据。

## 4 方案 A 操作上传加游标变更流

### 4.1 核心模型

客户端把每次离线修改保存为不可变 `SyncOperation`，上传给服务端。服务端对操作完成幂等判定、权限校验、revision 检查和冲突处理，然后写入当前资源状态，并在同一事务中追加一条账号级变更记录。客户端用服务端游标增量拉取变更。

这不是完整事件溯源。操作表可以按幂等窗口清理，业务真相仍是当前资源表；变更流用于同步复制而不是永久重建全部历史。

### 4.2 建议请求模型

```text
POST /sync/push
Authorization: Bearer <access-token>
X-Sync-Protocol: 1

{
  deviceId,
  clientBatchId,
  operations: [
    {
      operationId,
      itemType,
      itemId,
      documentIdentityId,
      documentVersionId,
      baseRevision,
      operationType,
      payload
    }
  ]
}
```

服务端逐项返回：

- `APPLIED`：操作已应用，返回新 revision 和对应变更序号。
- `ALREADY_APPLIED`：重复操作，返回原结果，不再次产生副作用。
- `CONFLICT_COPY_CREATED`：笔记冲突，返回主版本和冲突副本 ID。
- `STALE_PROGRESS_IGNORED`：进度较旧，操作被确定性消费但不覆盖当前值。
- `TOMBSTONED`：对象已删除，旧 upsert 被拒绝。
- `REAUTH_REQUIRED`：令牌或设备会话无效，整批不得继续写入。
- `REBASE_REQUIRED`：账号数据世代或协议基线已经变化。
- `VALIDATION_REJECTED`：字段、长度、DocumentVersion 或权限不合法。
- `RETRYABLE`：暂时性失败，操作保留在本地队列。

拉取接口：

```text
GET /sync/pull?cursor=<opaque>&limit=<n>

{
  changes: [...],
  nextCursor,
  hasMore,
  syncEpoch,
  protocolVersion
}
```

游标应是不透明令牌或至少与账号、数据世代绑定，客户端不能自行构造或解释。

### 4.3 服务端事务边界

单条操作至少需要在一个数据库事务中完成：

1. 校验账号和设备会话。
2. 读取或登记 `operationId` 幂等记录。
3. 锁定或条件更新目标资源 revision。
4. 写入资源、冲突副本或 tombstone。
5. 追加账号变更流记录并分配单调序号。
6. 保存操作结果供超时重放查询。

如果步骤 3 至 6 不能原子完成，可能出现资源已变更但拉取流缺记录，或者操作返回成功却无法被其他设备看到。

### 4.4 客户端同步周期

一次同步可以按以下顺序执行：

1. 检查登录和设备会话。
2. 拉取远程变更，避免先删除本地操作后失去冲突上下文。
3. 在本地事务中应用远程变更并推进游标。
4. 上传有界本地操作批次。
5. 根据逐项结果删除、保留或转入冲突/终态队列。
6. 再次拉取，取得自己或其他设备刚产生的服务端规范化结果。

也可以先上传再拉取，但必须保证本地保留足够的 base 状态用于冲突解释。具体顺序应通过测试确定并写入共享状态机，而不是散落在 UI 中。

### 4.5 客户端状态机

建议区分对象状态与同步会话状态。

对象状态：

- `SYNCED`：本地已应用到已知服务端 revision。
- `DIRTY_QUEUED`：本地操作已持久化，等待上传。
- `UPLOADING`：操作处于一次请求中，仍不能从队列删除。
- `RETRYABLE_ERROR`：网络、超时、限流或服务暂不可用。
- `REJECTED`：校验、权限或协议错误，需要用户或升级处理。
- `CONFLICT`：存在冲突副本，需要用户选择或保留双方。
- `DELETED_PENDING`：本地删除已入队，但尚未获服务端确认。
- `TOMBSTONED`：已接收服务端删除状态，旧编辑不能恢复。

同步会话状态：

- `IDLE`
- `PULLING`
- `APPLYING_REMOTE`
- `PUSHING`
- `BACKING_OFF`
- `REAUTH_REQUIRED`
- `REBASE_REQUIRED`
- `PROTOCOL_UPGRADE_REQUIRED`

### 4.6 重试与退避

- 网络断开、连接超时、HTTP 429、服务端 5xx：保留操作，指数退避加抖动。
- HTTP 401：暂停同步，刷新令牌；刷新失败进入 `REAUTH_REQUIRED`。
- HTTP 403 或设备撤销：进入终态，不自动循环刷新。
- 字段校验错误：逐项 `REJECTED`，不得无限重试。
- 请求超时但服务端可能已提交：使用相同 operationId 重放，不能生成新 ID。
- `Retry-After` 存在时优先遵守，但仍设置客户端最大退避上限。

### 4.7 游标失效和重新基线

D-19 A 允许 tombstone 在固定周期后清理，因此服务端需要 `syncEpoch` 或最早有效游标：

- 游标仍有效：继续增量拉取。
- 游标过旧：返回 `REBASE_REQUIRED`，同时说明当前 epoch。
- 客户端先冻结上传队列，下载账号当前同步快照或分页资源清单。
- 本地未上传操作不得丢弃；应对照新基线重新验证 baseRevision。
- 基于旧 tombstone 前状态的操作必须被拒绝或进入人工处理，不能自动覆盖。

仅返回“cursor not found”而让客户端清空数据是不合格的恢复策略。

### 4.8 收益

- 与离线队列、D-13 A 冲突规则和 tombstone 传播自然匹配。
- 一个账号级游标可以覆盖笔记、进度、冲突副本和删除。
- 客户端请求数可通过批次控制，适合移动网络。
- 现有实验已经验证 operationId、持久队列、游标和进程恢复的最小概念。

### 4.9 可行性与实施难度

- 可行性：高。
- 实施难度：中到高。
- 客户端复杂度：中，需要持久队列、本地事务和明确状态机。
- 服务端复杂度：中到高，需要幂等表、资源 revision、账号变更流和游标清理。
- 实验成本：中，需要真实数据库和服务端测试，但不要求消息中间件。

### 4.10 风险及验证

- 风险：资源状态和变更流写入不原子。
- 风险：幂等记录过早清理，超时重放产生重复副作用。
- 风险：客户端错误地在应用远程变更前推进游标。
- 风险：变更流无限增长或快照重建过慢。
- 验证：提交后丢响应、重复操作、乱序、部分失败、崩溃点注入、游标过期和协议升级。

## 5 方案 B 资源版本条件更新加周期拉取

### 5.1 核心模型

客户端直接对笔记、进度等资源执行 `PUT/PATCH/DELETE`，使用 revision 或 ETag 条件更新。远程变化通过按资源类型分页、更新时间水位或 revision 列表拉取。

典型接口：

```text
PUT /notes/{id}
If-Match: <revision>
Idempotency-Key: <operationId>

GET /notes?changedAfter=<watermark>&pageToken=...
GET /progress?changedAfter=<watermark>&pageToken=...
```

### 5.2 冲突和删除

- 笔记条件更新失败时，服务端可以创建冲突副本或返回当前版本让客户端另行创建。
- 进度使用服务端 revision 或变更序号比较，不能依赖客户端时间。
- DELETE 实际写入 tombstone；所有资源列表必须包含删除标记，否则其他设备无法清理本地对象。

### 5.3 拉取水位的技术问题

按 `updatedAt` 拉取看似简单，但存在以下风险：

- 多条记录具有相同时间戳，分页边界可能漏数据。
- 数据库和应用服务器时钟不同。
- 跨资源类型无法形成一个一致的全局水位。
- 删除后硬删除的记录无法再由普通资源查询返回。

若为解决这些问题加入全局单调变更序号，方案 B 会逐渐接近方案 A，只是上传仍采用资源接口。

### 5.4 客户端状态机

对象状态与方案 A 相似，但同步会话通常需要按资源类型分别跟踪水位：

- `PULLING_NOTES`
- `PULLING_PROGRESS`
- `PULLING_TOMBSTONES`
- `PUSHING_NOTE`
- `PUSHING_PROGRESS`

状态数可能少于操作批次协议，但多资源水位和部分失败会增加组合状态。

### 5.5 收益

- 资源接口直观，容易手工调试和展示。
- 服务端当前状态模型简单，可直接使用条件更新。
- 对小规模、弱离线需求的系统实施成本较低。

### 5.6 可行性与实施难度

- 可行性：高。
- 实施难度：中。
- 客户端复杂度：中，多资源类型需要分别调度。
- 服务端复杂度：中，若采用可靠全局水位则上升。
- 实验成本：低到中。

### 5.7 风险及验证

- 风险：分页和时间水位漏掉变更。
- 风险：多资源请求较多，离线操作集中恢复时效率低。
- 风险：删除传播、冲突副本和跨资源一致顺序不自然。
- 风险：加入全局变更表后与方案 A 的复杂度差距变小，却保留更多接口分支。
- 验证：相同时间戳分页、跨页删除、资源类型乱序、条件更新冲突和大量离线操作。

## 6 方案 C 追加事件日志复制

### 6.1 核心模型

每次笔记修改、进度变化、删除、恢复或冲突都作为不可变领域事件追加。客户端与服务端复制事件流，当前资源状态由投影或快照重建。

这比方案 A 更强：方案 A 的操作和变更流可以按窗口清理，当前资源表是业务真相；方案 C 的事件日志是业务真相。

### 6.2 技术要求

- 事件 ID、聚合 ID、事件序号、设备 ID、因果 revision、模式版本。
- 投影、快照、重建、压缩和事件模式迁移。
- 删除时对历史敏感内容的净化、加密密钥销毁或法规例外策略。
- 客户端必须处理未知事件版本或被服务端要求升级。

### 6.3 冲突和删除

- 冲突可通过保留并发事件和确定性投影规则表达。
- tombstone 是事件之一，但历史 upsert 事件仍可能包含已删除正文。
- 若 D-19 要求硬删除正文，必须重写事件历史、销毁每对象密钥或把敏感载荷移出事件日志。这会削弱纯事件溯源的简单性。

### 6.4 收益

- 审计、重放、故障分析和历史恢复能力最强。
- 对未来复杂协作和字段级合并有演进空间。
- 可以精确解释状态如何产生。

### 6.5 可行性与实施难度

- 可行性：中。
- 实施难度：高。
- 客户端复杂度：高，需要事件兼容和投影。
- 服务端复杂度：高，需要事件存储、快照、投影和修复工具。
- 实验成本：高，必须测试重放、快照、模式迁移和隐私删除。

### 6.6 风险及验证

- 风险：为个人低并发同步引入过度复杂的事件基础设施。
- 风险：敏感笔记长期残留在不可变历史中，与硬删除冲突。
- 风险：投影错误或模式迁移错误影响所有状态重建。
- 验证：从零重放、快照前后等价、跨版本事件、删除净化和损坏投影恢复。

## 8 实验成本和必要性

### 8.1 方案 A 的必要实验

必须实现一个真实但最小的同步服务和数据库事务，不需要部署消息队列：

- 幂等操作表。
- 笔记、进度和 tombstone 资源表。
- 账号级变更序号表或变更日志表。
- push/pull 两个最小接口。
- 提交后丢响应、游标推进崩溃点、部分失败和长期离线测试。

预计成本主要在事务正确性和测试向量，而不是基础设施安装。

### 8.2 方案 B 的必要实验

可以使用普通 REST 资源接口验证，但必须专门证明分页不会漏变更：

- 条件更新和 Idempotency-Key。
- 笔记、进度、tombstone 三类拉取。
- 相同时间戳、多页、跨资源和删除样本。
- 若实验最终引入全局变更序号，应重新评估是否直接采用方案 A。

### 8.3 方案 C 的必要实验

仅实现“追加一条事件”不足以证明方案可用。至少需要：

- 状态投影和从零重建。
- 快照与日志压缩。
- 事件模式升级。
- 删除正文的历史净化或密钥销毁。
- 投影损坏恢复。

其成本显著高于当前个人账号、低并发和课程周期所直接提出的问题。

## 9 与 D-26、D-27、D-30 的边界

- D-21 决定同步业务语义和客户端状态机。
- D-26 决定后台同步任务如何调度、取消、重试和跨进程恢复。
- D-27 决定公共接口采用 REST、流式或轮询，以及错误模型和协议版本表达。
- D-30 决定关系数据库、队列、缓存和变更表的具体实现。

选择 D-21 A 不等于必须使用 Kafka、RabbitMQ 或事件总线。账号变更流可以由同一关系数据库事务中的表和单调序号实现。

## 10 选择时需要明确的附加约束

无论选择 A、B 或 C，建议同时确认以下约束是否接受：

1. 游标和 revision 由服务端生成，客户端时间不参与冲突胜负。
2. 上传接口逐项返回结果，允许一批中部分成功。
3. 请求超时后使用相同 operationId 重放。
4. tombstone 过期导致游标失效时，客户端执行重新基线，不清空未上传队列。
5. 设备撤销为终态错误，不自动重新注册为同一设备。
6. 一期不要求实时推送；应用启动、回到前台、用户触发和后台机会任务可以触发同步。
7. 推送通知若后续加入，只是“有变化”的提示，不承载业务数据或替代拉取。
8. 协议至少包含 `protocolVersion`、`syncEpoch` 和最低支持客户端版本。

## 11 集中选择格式

请由当前对话人选择：

`D-21 A / B / C`

也可以附加约束，例如：

`D-21 A；接受第10节全部约束；一期不做实时推送。`
