## 3 B-D01 Windows 平台架构约束清单

### 3.1 文件选择、路径与「授权」恢复

【W实测 + W官方】Windows 桌面应用没有 Android SAF 那类「按 URI 的持久授权」。用户通过系统文件对话框（Common Item Dialog）或拖放选择一个**路径**，应用随后以当前用户令牌 + 文件 ACL 访问；能读多久取决于文件是否存在、ACL 是否仍允许、以及是否被独占打开，而不是平台发放的授权凭据。本轮探针直接测得：

- 文件被移动后，旧路径立即不存在，按旧路径重新打开失败，内层异常为 `System.IO.FileNotFoundException`；
- 文件被删除后，路径与内容都不可恢复；
- 文件被设为只读时，覆盖写抛 `UnauthorizedAccessException`，内容与哈希不变；
- 文件被其他进程以 `FileShare.None` 打开时，第二次读写打开抛 `System.IO.IOException`。

架构影响：

1. 「文件授权」在 Windows 端退化为「路径可访问性 + 身份校验」，必须作为独立职责域处理失效与重新绑定（对应 FR-01、BR11、NFR-13、AC-01/AC-02、D-05 的「两端分别重新授权」）。
2. `DocumentIdentity` 不能只用路径。建议组合「源哈希 + 规范化元数据（大小、修改时间、格式）」；Windows 另可提供卷序列号与文件 ID（`BY_HANDLE_FILE_INFORMATION` / `FILE_ID_INFO`），能在同卷移动/改名后保持稳定，可用于「疑似同一文件已移动」的提示而非自动信任（【W官方】+【W推断】，D-16 输入）。
3. 读取源文件应使用宽松共享模式（允许其他进程读写），否则与 Office、PDF 阅读器、同步客户端共用文件时会互相阻塞；写入侧只写用户指定目标，绝不回写源文件（BR07、NFR-13）。
4. 拖放只能拿到路径或 `IDataObject`，安全性等同于用户选择的路径；仍需走同一身份与格式校验，不能跳过「不支持格式/无权限」提示（AC-01）。

### 3.2 安装版与便携版对文件访问、运行时与数据目录的影响

【W官方 + W推断】Windows 桌面制品有四种常见形态，对架构影响不同（形态与权限来自官方资料，「对本项目的含义」为本文档推断）：

| 形态 | 典型位置 | 权限 | 数据目录 | 对本项目的含义 |
|---|---|---|---|---|
| 每用户安装（MSI/EXE，`per-user`） | `%LOCALAPPDATA%\Programs\...` | 无需管理员 | `%LOCALAPPDATA%\<App>` | 课堂演示最省事，升级覆盖风险低 |
| 每机器安装（MSI/EXE，`per-machine`） | `%ProgramFiles%` | 安装需管理员 | `%LOCALAPPDATA%` 或 `%APPDATA%` | 安装/卸载需提权，不适合无管理员环境 |
| MSIX 打包 | 系统管理 | 需受信任证书签名 | 虚拟化/重定向 | 签名与证书是课程额外负担 |
| 便携版（解压运行） | 任意用户可写目录 | 无需安装 | 程序目录旁或 `%LOCALAPPDATA%` | 与 D-08「解压运行演示包」直接对应 |

本轮探针确认本机 `%LOCALAPPDATA%` 存在、进程未提权、`Program Files` 为标准路径（【W实测】）。架构结论：

1. 一期优先「每用户安装或便携版 + 数据写 `%LOCALAPPDATA%`」，避免管理员权限成为演示阻塞项（D-08）。
2. 便携版不得把用户笔记/索引写进程序目录：程序目录可能只读、可能被整体替换、也可能被搬到 U 盘；数据目录必须可配置且与程序分离。
3. 安装版升级覆盖时要保留 `%LOCALAPPDATA%` 数据与同步游标；卸载默认不删用户数据，需在卸载说明中显式告知（对应 D-19 的本地删除语义）。

### 3.3 多窗口、键盘鼠标、高 DPI 与缩放

【W实测 + W官方】本轮探针测得本机为单显示器、`AppliedDPI=144`（150% 缩放），逻辑分辨率 1707×1067。Windows 的 DPI 模型要求应用清单声明感知级别（推荐 Per-Monitor V2），否则系统会对窗口做位图拉伸，导致文本模糊、命中坐标偏移。

架构影响：

1. bbox 与选区命中必须使用**与渲染同一坐标系**的逻辑坐标；DPI 变化（拖到另一块屏、用户改缩放）会触发 `WM_DPICHANGED`，需要重新计算缩放与缓存坐标。单屏 150% 的实测不能覆盖混合 DPI，登记为【待测】。
2. 桌面交互以鼠标 hover、拖拽选词、右键菜单、滚轮与键盘快捷键为主，和 Android 的触摸选区是两套交互边界；平台适配层应各自实现，不把选区逻辑放进共享核心。
3. 多窗口（阅读窗口 + 笔记窗口）会引入同一文档的多视图状态同步；一期建议单主窗口 + 侧栏，避免多窗口一致性问题（架构简化建议，非决策）。

### 3.4 应用关闭、窗口关闭、系统重启与长任务恢复

【W官方 + W推断】Windows 桌面进程没有 Android 的 WorkManager/Doze 机制：进程退出、注销、关机或崩溃后，内存中的解析/索引/同步任务即消失。系统关机时应用只有很短的收尾时间，长任务不能假设能优雅完成。

架构影响：

1. 解析、OCR、索引、导出、同步重试必须是**本地持久任务**（任务表 + 状态机 + 幂等键），应用启动时扫描未完成任务并续跑或标记失败（对应 NFR-04、D-26）。
2. 「应用关闭」需要区分「窗口关到托盘/后台」与「真正退出」；一期建议关闭即退出并提示未完成任务，不做常驻后台，避免与「无后台服务」的课程范围冲突。
3. 单实例约束：两个实例同时写同一个本地数据库会触发 SQLite 锁冲突，应使用单实例互斥（命名 Mutex）或明确的多实例锁策略（【W推断】）。
4. 崩溃恢复只能依靠持久状态和日志；不得把「上次运行内存态」当作可靠状态（D-21 输入）。

### 3.5 凭据、令牌与本地敏感数据的安全存储

【W实测 + W官方】本机存在 `cmdkey.exe`、`%APPDATA%\Microsoft\Credentials` 与 DPAPI 主密钥目录 `%APPDATA%\Microsoft\Protect`。Microsoft 官方对 Windows 本地秘密存储的推荐顺序是：优先消除口令（Windows Hello/通行密钥/证书），其次使用 Windows Credential Manager（`CredWrite`/`CredRead`，由用户登录会话密钥加密），再次使用 DPAPI（`CryptProtectData`）加密必须本地持久化的秘密。

架构影响：

1. 令牌与刷新令牌必须放 Credential Manager 或 DPAPI 保护的文件，不得明文写配置文件、日志或崩溃报告（对应 D-18、D-31）。
2. DPAPI 与用户账户绑定：换用户、重装系统或把便携版拷到另一台机器后密文不可解，需要重新登录。这是可接受的降级路径，但必须在用户可见状态中说明。
3. 「共享核心只定义凭据读写契约，平台适配层各自实现」——Windows 的 Credential Manager/DPAPI 与 Android Keystore 是两个不同实现（与 C 文档 3.5 结论一致）。
4. 笔记可能包含原文摘录，属潜在敏感数据，本地存储加密边界属 D-20，本文档只登记平台能力，不决定是否全库加密。

### 3.6 Markdown 与 PDF 导出的目标位置与覆盖行为

【W实测 + W官方】本轮探针测得：普通覆盖写会直接替换目标文件，**不会自动保留旧版本**；同目录不会产生备份文件。系统「另存为」对话框通常自带覆盖确认，但确认后仍是直接替换。

架构影响：

1. 导出流程必须自己实现：目标位置选择（用户显式指定）→ 覆盖确认 → 写入 → 结果反馈 → 失败不静默覆盖（对应 FR-09、AC-20、D-10）。
2. 导出内容必须携带来源版本与引用信息（页码/章节/原文片段），否则跨端导出语义不一致（D-10）。
3. 导出目录可能位于 OneDrive/网盘同步目录，写入即意味着内容离开本机；应在导出提示中说明，不能把「导出到本地目录」等同于「数据未出设备」（D-05/D-17 边界提醒）。
4. PDF 导出的版式一致性依赖导出库与字体；Markdown 导出相对可控。二者都需要固定样本比对（B-D05）。

## 4 B-D03 Windows 文档能力与引用链分析

### 4.1 格式与解析路线

一期格式为 PDF、DOCX、Markdown 与扫描文档（OCR）。Windows 端候选能力盘点：

| 格式 | 候选能力（Windows） | 已观察结果 | 关键风险 | 证据等级 |
|---|---|---|---|---|
| 文本型 PDF | PyMuPDF（页/块/bbox/阅读顺序）；pdfplumber（字符/线/矩形/表格）；Docling（布局/表格/结构）；Apache Tika（Java，MIME+扁平文本） | 三份自制样本字符召回均 1.0；PyMuPDF 双栏严格段落边界召回 0.2857；Docling 标题 F1 0.80–0.9091、表格单元格 0.7778、脚注召回 0；Tika 无元素级页码/bbox | 「能抽文本」≠「结构正确」；双栏与脚注不可静默当事实 | 【W实测】`TECH-DOC-007-R02-MANUAL-SCORE` |
| DOCX | python-docx（样式/表格，无视觉分页）；Apache POI（Java） | 能读 12 段 + 1 表；视觉页码不可直接获得 | 分页/脚注/页眉页脚需另做映射 | 【W实测】`TECH-DOC-001-R01` |
| Markdown/TXT | CommonMark/GFM 解析器（markdown-it-py）；编码探测 | CommonMark 识别 4 个标题与行区间；GB18030 先 UTF-8 失败再回退 | GFM 表格/脚注/公式扩展未验证 | 【W实测】`TECH-DOC-001-R01` |
| 扫描件 OCR | Tesseract、RapidOCR 3.9.2 + ONNX Runtime、PaddleOCR/PP-Structure、EasyOCR、ocrmypdf | 清晰两页 RapidOCR 144 DPI 达暂定门槛；公开图片 11 问 RapidOCR 4/11、Tesseract 3/11 | 退化页、旋转、表格、印章不可自动进精确问答 | 【W实测】`TECH-OCR-022/024` |

架构影响：

1. 不能用单一解析器覆盖全部格式与全部结构要求；一期至少需要「低层坐标解析 + 结构解析 + 原始结果保留」的组合（与 `TECH-DOC-007` 结论一致）。
2. 解析结果的 IR 必须保留 `document_id/version_id/source_hash/parser_version/config_hash/page/block/section_path/char_start-end/bbox/confidence`（NFR-05、AC-06）。
3. 组件差异会直接污染引用链：同一页面不同组件的 block 切分、坐标与阅读顺序不可互换（D-22、D-25 输入）。

### 4.2 渲染、选择、搜索、目录、页码、bbox 与引用回跳

【W推断 + 待测】Windows 端的关键未知量不是「能不能抽文本」，而是「桌面 UI 里的选择与回跳」：

- 若渲染组件与抽取组件分离（例如 PDFium/WebView2 渲染 + PyMuPDF 抽取），两套坐标必须做统一映射；否则高亮框会偏移。
- 引用锚点建议「字符范围 + 结构锚点（block_id/section_path）+ 文本校验」多锚点冗余，bbox 仅用于页面回显，不作为唯一锚点（D-25）。
- 目录是派生对象，其还原率取决于标题识别质量；Docling 层级全为 1、脚注召回为 0 的实测说明「目录候选」必须可校验、可降级（对应 AC-04）。
- 页码同时存在「物理页」与「打印页码标签」两种语义，引用必须同时保存，不能只存其一（NFR-01、AC-06）。

本轮可给出的判断：Windows 端**页级与块级证据链在库层已经可观察**（页码映射率 1.0、bbox 越界检查通过，`TECH-CIT-FOLLOWUP-R01`），但**证据契约完整率为 0**（缺版本、源哈希、字符偏移），说明「定位」与「契约」是两件事，桌面端必须把契约校验放在门控里（`TECH-RET-007-R01`）。

### 4.3 桌面资源预算

【W实测 + W推断】Windows 桌面资源通常优于 Android，但并非无限：

- 索引与 OCR 占用 CPU 会与阅读渲染争抢，导致 UI 卡顿；需要后台线程 + 进度 + 取消（NFR-11、NFR-12）。
- 20 份文档候选上限（NFR-06）在 Windows 上尚无可比实测；不得用 Android 数据外推，反之亦然（D-33 要求分别报告）。
- 首次运行需要下载/解压 OCR 模型与 embedding 模型时，磁盘与网络成本必须可预算，不能默认联网下载（课程演示环境可能断网）。

### 4.4 渲染组件、抽取组件与共享核心的边界

| 边界 | 建议归属 | 理由 |
|---|---|---|
| 文件选择与路径授权 | Windows 平台适配 | 平台原语，无跨端共性 |
| 页面渲染与选区交互 | Windows 平台适配（或 WebView 内 PDF.js） | 与 UI 框架强耦合 |
| 低层解析（页/块/bbox/字符偏移） | 平台适配或共享核心二选一，但**契约必须共享** | 保证双端 IR 一致（D-22） |
| 结构校验、分块、索引、检索、证据契约、引用校验 | 共享核心 | 业务语义与可测试性（D-03） |
| 导出文件写入 | Windows 平台适配 | 目标选择与覆盖行为是平台语义 |

结论：**共享核心只应承载「文档无关」的契约与规则**；任何把具体 PDF 库类型泄漏进共享核心的做法，都会使另一端无法实现同一契约（与 C 文档 4.4 一致）。

### 4.5 文档能力汇总

| 能力 | Windows 现状判断 | 证据等级 |
|---|---|---|
| PDF 文本/页/bbox | 库层可用且有实测 | 【W实测】 |
| PDF 双栏阅读顺序 | 不可靠，需结构校验 | 【W实测】 |
| PDF 表格/脚注 | 部分可用，需降级 | 【W实测】 |
| DOCX 结构 | 可用，视觉分页需另做 | 【W实测】 |
| Markdown/TXT | 可用，扩展未验 | 【W实测】 |
| OCR | 有限可用，低置信必须降级 | 【W实测】 |
| 桌面渲染内选区与高亮 | 未验证 | 【待测】 |
| 引用回跳（版本+页+块+字符） | 契约字段已有要求，桌面端未打通 | 【待测】 |

## 5 B-D02 Windows 候选路线比较矩阵

### 5.1 前提与分层

按 D-03，共享核心只覆盖领域模型、业务规则、数据契约与可测试核心，UI 与平台适配分别实现。比较时必须区分四个层次，不得混为同一层面的技术选项：

| 层次 | 内容 | 选择后果 |
|---|---|---|
| 共享核心能力 | 领域规则、同步状态机、证据契约、索引/检索契约 | 由 D-28 定 |
| Windows UI 壳 | Compose Desktop / WebView2+HTML / QML | 影响交互、性能、包体 |
| 平台文档组件 | PDFium、PDF.js、PyMuPDF、Qt PDF、Tika/POI | 影响引用链与许可证 |
| 服务端能力 | 身份、同步、AI 网关、审计 | 由 D-11/D-14 定 |

### 5.2 三条候选路线

- **路线 A：KMP 共享核心 + Windows JVM/Compose Desktop 平台实现**。共享核心用 Kotlin Multiplatform common 代码；Windows 壳为 JVM + Compose Desktop（Skia 渲染），用 jpackage/jlink 打包。
- **路线 B：共享 Rust 核心 + Windows Tauri/WebView2 平台实现**。共享核心用 Rust（解析/索引/同步状态机），经 Tauri 命令/FFI 暴露给 WebView2 前端；UI 用 Web 技术栈。
- **路线 C：Qt 路线（对照或平台实现）**。C++/QML 全栈，Qt PDF（基于 PDFium）可作文档能力上限对照；若共享大量 QML UI 则偏离 D-03。

### 5.3 统一比较矩阵（12 维度 × 3 路线）

| 维度（A-04） | A：KMP + Compose Desktop | B：共享 Rust + Tauri/WebView2 | C：Qt（对照） |

### 5.4 结论与证据等级

- 三条路线在 Windows 上均「可行但未在桌面壳层实测」，正式结论须以 D-12 获批实验为准。
- 就「共享核心 + 分端 UI」这一 D-03 目标而言，**路线 A 的桥接与工具链成本最低**，且与本项目已有的 JVM 最小链路（`TECH-ARCH-001~004`）同构，是下一轮最小工程的首选基线。
- **路线 B 的优势是包体与 WebView 生态**（PDF.js 的文本层能显著降低选区/回跳实现成本），代价是 Rust + 前端双栈与命令边界；若 D-12 选择 B，应把「PDF.js 文本层坐标 ↔ 共享锚点契约」列为第一验证项。
- **路线 C 的 Qt PDF 是文档能力上限对照**，不建议作为共享核心主线：许可、包体与 C++ 工具链成本高，且大量 QML 共享会偏离 D-03。
- 上述均为架构级推断，**不能替代 Windows 桌面最小工程验证**。

## 6 B-D04 Windows 同步与离线场景分析

### 6.1 本地数据持有边界

【W推断】本地优先语义与 Android 一致：文档本体、全文索引、解析缓存、笔记、进度、同步队列元数据均保留在设备本地；云端只同步最小身份、进度、笔记、文档身份与版本元数据（D-05、D-17）。Windows 差异在于：

- 本地数据位于 `%LOCALAPPDATA%` 或用户配置的数据目录，**卸载不自动清理**，换机/重装后需云端重同步；
- 源文件仍在用户原位置，应用只持有路径与身份，不复制进数据目录（与 D-05 一致）。

### 6.2 离线修改与同步队列

【W推断 + 待测】Windows 没有 Android 的后台调度：离线修改只能写入本地持久队列，并在**应用下次启动或本次运行期间**消费。

- 队列项需含 `operation_id`、`device_id`、`base_revision`、`item_type`、`payload_hash`，保证重试幂等（D-21）。
- 应用关闭即停止同步，用户可见状态必须区分「已保存本地」与「已同步云端」，不能把两者混为一个「保存成功」（NFR-09、AC-23）。
- 断网、代理故障、VPN 切换都会让请求表现为超时或证书错误；重试需指数退避并保留失败原因（D-27 输入）。

### 6.3 路径变化、文件替换与版本不匹配

【W实测 + W推断】路径失效是 Windows 常态（本探针已测移动/删除后的失效行为）。识别策略：

| 场景 | 识别手段 | 处理 |
|---|---|---|
| 同卷移动/改名 | 卷序列号 + 文件 ID 与已存身份比对 | 提示「疑似同一文件已移动」，用户确认后重绑 |
| 另一台设备/另一路径 | 源哈希 + 规范化元数据 | 匹配则复用文档身份，不匹配则新建版本或独立文档（D-16） |
| 内容被替换（同路径不同内容） | 源哈希变化 | 新建 `DocumentVersion`，旧索引/引用标 stale（BR05） |
| 文件被删除/撤权 | 路径不存在或访问被拒 | 停止活动任务、索引标 stale、引用显示失效（D-19） |

### 6.4 账号退出、设备撤销、文件撤权与本地残留

【W推断】需要区分三种「退出」：

1. **账号退出**：清除令牌与凭据（Credential Manager/DPAPI 条目），本地笔记与索引是否保留由 D-18/D-19 决定；
2. **设备撤销**：服务端拒绝该设备令牌，客户端进入「重新登录」状态，不得继续上传；
3. **文件撤权/删除**：应用失去路径访问或文件不存在，必须停止对该文档的新检索与模型调用，历史引用标失效（分工方案 2.3 第 6 条、BR05）。

本地残留清理必须覆盖：解析缓存、OCR 中间图、导出临时文件、日志中的路径与查询。本机探针只能证明凭据目录存在，**实际清理行为待测**（D-20）。

### 6.5 同步失败、重复提交、游标失效与冲突副本

【W推断】桌面端的用户可见状态至少需要：等待同步、同步中、已同步、同步失败（可重试）、冲突（保留副本）、游标失效（全量重建）。

### 6.6 D-13 决策输入（冲突策略的 Windows 侧影响）

| D-13 候选 | Windows 侧影响 | 证据等级 |
|---|---|---|
| A 笔记保留冲突副本 + 进度最新有效 + tombstone | 需要冲突列表/副本查看/手动合并；桌面大屏适合并排 diff，交互成本低于移动端 | 【W推断】 |
| B 字段级合并/CRDT | 富文本、引用锚点、重排语义复杂；桌面端实现可行但测试成本高 | 【待测】 |
| C 全部 LWW | 实现最简；但桌面端长时间离线（关机数天）后重连，静默覆盖风险高，且用户可能手动改系统时间，时钟偏差更现实 | 【W推断】 |

> B 的建议倾向：从「个人、低并发、不静默丢笔记」出发倾向 A；Windows 侧必须补充「关机数天后重连」「手动改时钟」「同一文件被外部程序替换」三类场景的验证，再由 A 汇总（最终由项目负责人批准）。

## 7 B-05 Windows AI 调用与降级

### 7.1 本地检索、证据选择、逐文件同意与云端生成的边界

【W实测 + W推断】既有实验已证明「证据门控 → 云端适配器 → 引用校验」这条链路在 Windows 上可运行：门控拒绝的 4 类用例 CLI 调用次数为 0，完整合成证据用例一次调用返回合法 JSON（`TECH-ARCH-004-R01`，约 7.1 秒）。

Windows 端的边界补充：

1. 逐文件同意必须在桌面 UI 上显式呈现「文件、版本、模型服务、用途、策略版本」，且不可复用为永久授权（NFR-08、AC-08）。
2. 同意状态与审计事件写在本地并同步云端；退出登录后不得残留「已同意」缓存（D-31）。
3. 默认不发送整份文件；只发送通过 Evidence Contract 的最小证据（BR02、BR03）。

### 7.2 流式响应、取消、超时、供应方错误与断网

【W推断 + 待测】Windows 特有的干扰项：

- **系统代理与 TLS 拦截**：企业代理可能中断 SSE 长连接或注入自签证书，导致流式失败；需要可配置代理与清晰的错误分类（D-27）。
- **睡眠/休眠**：笔记本合盖后连接中断，恢复时必须把「半条回答」标为失败而不是部分成功（NFR-04）。
- **取消**：取消必须真正中止请求与本地后续处理，不能只隐藏 UI。
- **超时**：30 秒首反馈、1 分钟完成仍是候选目标，未实测前不得写成 SLA（NFR-10、D-33）。

### 7.3 断网/模型不可用时保持阅读、笔记与本地检索

【W实测 + W推断】`TECH-ARCH-003/004` 已验证云端失败时回退本地证据与原文阅读；`TECH-RET-*` 证明本地检索链路可运行。Windows 端要求：

- 断网时仍能打开已导入文档、阅读、检索已建索引、查看笔记（NFR-09、AC-23）；
- AI 入口显示明确降级状态（本地证据/原文/拒答），不得报「系统不可用」；
- 本地生成模型不在一期范围（D-06、FR-12）。

### 7.4 日志、崩溃报告与隐私字段

【W推断】Windows 崩溃转储（WER）与日志易混入文件路径、查询文本、证据片段：

- 结构化日志只记录 ID、状态、错误码、耗时，不记录原文与查询（D-32）；
- 崩溃报告默认不上传；若启用，必须先脱敏并排除路径与凭据；
- 本地日志保留期与清理规则需在 D-31/D-32 中决定。

### 7.5 D-15 决策输入

- 单一供应方（A）：Windows 侧验证面最小，需验证超时/限流/取消/替换桩与代理场景（【待测】）。
- 主备供应方（B）：切换需用户显式同意；桌面端要能显示「当前供应方」并记录切换事件（【待测】）。
- 自托管/校内端点（C）：桌面端主要影响是证书与网络可达性（校内网/VPN），需真实双端访问验证（【依赖D】）。

## 8 B-D05 Windows 发布验证计划

### 8.1 候选制品形式与运行时依赖

| 制品 | 构建工具 | 运行时依赖 | 体积风险 | 适用判断 |

【W官方】jpackage 的 `--type` 包含 `app-image`、`exe`、`msi`，必须在目标平台构建，msi/exe 依赖 WiX 3.0 及以上；【W官方】Tauri 的 MSI 由 WiX v3 生成且仅能在 Windows 构建，NSIS 安装器可跨平台。

### 8.2 清洁 Windows 11 环境的安装、首次启动、升级、覆盖与卸载

验证必须在一台「未装过本项目、未装运行时」的 Windows 11 上执行：

1. **安装/解压**：记录来源（zip/msi/exe）、是否需要管理员、是否被 SmartScreen 拦截。
2. **首次启动**：冷启动耗时、首屏可交互、数据目录创建位置、权限提示。
3. **升级/覆盖**：同版本号覆盖、版本号递增覆盖，检查本地数据库迁移、同步游标保留、用户设置保留。
4. **卸载/删除**：程序文件清理、开始菜单/桌面快捷方式清理、`%LOCALAPPDATA%` 用户数据保留策略是否与说明一致、令牌是否被清除。
5. **残留检查**：注册表项、服务、计划任务、凭据条目、临时文件。

### 8.3 签名、版本号、崩溃日志、第三方许可证与依赖升级

- 课程演示包至少说明「未签名 → SmartScreen 提示」的预期，或使用自签名证书并在安装说明中给出信任步骤（【W官方】）。

- 崩溃日志需脱敏，路径与原文不得进入可外发日志（D-32）。

### 8.4 固定样本回归、自动化测试与证据可复现性

## 10 B-D06 架构建议与验证缺口

### 10.1 推荐倾向与适用条件

- **共享核心路线**：在不宣布最终技术栈的前提下，Windows 端证据更支持 **路线 A（KMP 共享核心 + Compose Desktop 平台实现）** 作为下一轮最小工程的首选基线——它与既有 JVM 证据（`TECH-ARCH-001~004`）同构、工具链单一、对 D-03「分端 UI + 共享核心」的桥接成本最低。
- **适用条件**：文档能力必须收敛到「共享核心只定义 IR/锚点契约 + Windows 适配层实现渲染与抽取」；若一期要求桌面端达到 Qt PDF 级别的选择/回跳体验，则路线 A 需要在渲染与选区上投入更多工作，需 D-12 实验数据支撑。
- **路线 B 的适用条件**：若 D-12 优先验证「跨语言核心 + WebView 前端」，则 B 的包体优势明显，但第一验证项必须是 PDF.js 文本层与共享锚点契约的一致性。
- **路线 C**：仅作为文档能力上限对照与备选平台实现，不建议作为主线。

### 10.2 反对理由与风险

- 路线 A 的主要风险是**桌面 PDF 渲染与选区需要自建**：Compose 没有内建 PDF 视图，bbox 命中、缩放、滚动与高亮都是自绘成本；这部分的工时不小于共享核心本身。
- 路线 B 的风险是**两套状态所有权**（Rust 核心与前端）与命令边界权限；WebView2 在受管控机器上可能被策略限制或缺失。
- 路线 C 的风险是**许可与工具链**：LGPL/商业许可、C++ 调试链、包体，且共享大量 QML 会偏离 D-03。
- 三条路线共同的风险是**没有桌面壳实测**：现有 Windows 证据都在库层，任何「已实现」的表述都不成立。

### 10.3 最小工程验证计划（下一轮 Windows 实验）

目标：用最小工程补齐「桌面壳 + 打包 + 文件交互 + 凭据 + 导出 + 离线」六类此前未覆盖的事实，而不是实现产品。建议至少覆盖：

> 落地状态：本轮只完成平台事实探针 `experiments/windows-env-probe/`（`TECH-WIN-001-R01`）。桌面壳最小工程因本机缺少 JDK/Maven/Rust/Node 工具链**尚未建立**，登记为【待测】；验证映射见 `../05-验证计划与证据索引/Windows端验证计划与证据索引.md`。

1. **桌面壳最小实验**：一个主窗口 + 固定 PDF 样本渲染 + 选区高亮 + 引用回跳，度量冷启动、内存、缩放（100%/150%/200%）下的命中。
2. **打包最小实验**：同一工程用 jpackage 生成 `app-image` 与 `msi`（或 Tauri 的 msi/nsis），度量包体、首次启动、依赖缺失表现。
3. **文件交互最小实验**：文件选择 → 读取 → 移动/替换/删除 → 重新选择与身份比对；记录各类失效的用户可见状态。
4. **凭据最小实验**：写入/读取/删除 Credential Manager 条目与 DPAPI 密文，验证换用户与重装后的不可解行为。
5. **导出最小实验**：Markdown/PDF 导出到用户目录、只读目录、网盘目录与已存在文件，验证覆盖确认、失败反馈与源文件不变。
6. **离线/降级最小实验**：断网启动 → 打开已导入文档 → 本地检索 → AI 入口降级状态。

每个实验需登记：样本、设备、Windows 版本/构建、缩放、计量口径、停止条件（对应 D-12 研究问题 4）。
