## 3 B-D01 Windows 平台架构约束清单

### 3.1 文件选择、路径与「授权」恢复（V1.1 按 D-16 A 修订）

【W实测 + W官方】Windows 桌面应用没有 Android SAF 那类「按 URI 的持久授权」：用户通过系统文件对话框或拖放选择一个**路径**，应用以当前用户令牌 + 文件 ACL 访问。`TECH-WIN-001` 测得：移动后旧路径立即失效（内层 `FileNotFoundException`）、删除后不可恢复、只读属性阻断写入（`UnauthorizedAccessException`）、被独占打开时并发写失败（`IOException`）。

`TECH-WIN-002` 进一步测得文件身份的判据：

- 复制到另一目录改名、移动改名：**SHA-256 不变**；
- 仅修改时间、字节不变：**哈希不变**；
- 同路径替换内容、同名文件被另一文件覆盖：**哈希改变**；
- 换行符 LF→CRLF：**哈希改变**（4 字节 vs 6 字节）；
- 删除后重建相同字节：**哈希相同**；
- 重复读取哈希稳定。

架构影响（与 D-16 A 对齐）：

1. **身份以精确内容哈希为主**，路径与修改时间只作展示与辅助提示。D-16 A 的「内容变化建立新版本」在 Windows 上可直接用哈希实现（对应 FR-01、AC-02、D-16 A）。
2. 路径失效仍需独立处理：哈希只能回答「是不是同一内容」，不能回答「文件在哪」。移动/改名后必须由用户重新选择，再用哈希确认是否同一文档（D-05「两端分别重新授权」在 Windows 的等价形式）。
3. 同一路径内容变化必须新建 `DocumentVersion`，并将旧引用标 stale（BR05、AC-18、D-25 A）；不得用「路径没变」推断版本未变。
4. 精确哈希是严格的：换行转换、重新导出、同义排版都会判为新内容。UI 必须提示「内容已变化，需重新生成引用」，避免用户误以为笔记被丢弃。
5. 读取源文件使用宽松共享模式（允许其他进程读写），否则与 Office、PDF 阅读器、同步客户端互相阻塞；写入只写用户指定目标，绝不回写源文件（BR07、NFR-13）。
6. 拖放只能拿到路径或 `IDataObject`，安全性等同用户选择，仍需走同一身份与格式校验（AC-01）。

### 3.2 安装版与便携版对文件访问、运行时与数据目录的影响

【W官方 + W推断】四种常见形态（形态与权限来自官方资料，「对本项目的含义」为推断）：

| 形态 | 典型位置 | 权限 | 数据目录 | 对本项目的含义 |
|---|---|---|---|---|
| 每用户安装（MSI/EXE，`per-user`） | `%LOCALAPPDATA%\Programs\...` | 无需管理员 | `%LOCALAPPDATA%\<App>` | 课堂演示最省事，升级覆盖风险低 |
| 每机器安装（MSI/EXE，`per-machine`） | `%ProgramFiles%` | 安装需管理员 | `%LOCALAPPDATA%` 或 `%APPDATA%` | 安装/卸载需提权，不适合无管理员环境 |
| MSIX 打包 | 系统管理 | 需受信任证书签名 | 虚拟化/重定向 | 签名与证书是课程额外负担 |
| 便携版（解压运行） | 任意用户可写目录 | 无需安装 | 程序目录旁或 `%LOCALAPPDATA%` | 与 D-08「解压运行演示包」直接对应 |

本机 `%LOCALAPPDATA%` 存在、进程未提权（【W实测】）。架构结论：

1. 一期优先「每用户安装或便携版 + 数据写 `%LOCALAPPDATA%`」，避免管理员权限成为演示阻塞项（D-08）。
2. 便携版不得把笔记/索引写进程序目录（可能只读、被整体替换或被搬到 U 盘）；数据目录必须可配置且与程序分离（D-20 A）。
3. 安装版升级覆盖要保留 `%LOCALAPPDATA%` 数据与同步游标；卸载默认不删用户数据，需在卸载说明中显式告知（D-19 A）。

### 3.3 多窗口、键盘鼠标、高 DPI 与缩放

【W实测 + W官方】本机单显示器、`AppliedDPI=144`（150% 缩放），逻辑分辨率 1707×1067；`TECH-WIN-001` 两次运行一致。Windows 要求应用清单声明 DPI 感知级别（推荐 Per-Monitor V2），否则系统位图拉伸导致文本模糊、命中坐标偏移。

架构影响：

1. bbox 与选区命中必须使用与渲染同一坐标系的逻辑坐标；DPI 变化触发 `WM_DPICHANGED`，需重算缩放与缓存坐标。单屏 150% 不能覆盖混合 DPI，仍为【待测】（W-E02/W-E12）。
2. 桌面交互以鼠标 hover、拖拽选词、右键菜单、滚轮与快捷键为主，与 Android 触摸选区是两套边界；平台适配层各自实现，选区逻辑不进共享核心（D-28 A）。
3. 多窗口会引入同一文档的多视图状态同步；一期建议单主窗口 + 侧栏（架构简化建议，非决策）。

### 3.4 应用关闭、窗口关闭、系统重启与长任务恢复（V1.1 按 D-26 A 修订）

【W官方 + W推断】Windows 桌面进程没有 Android 的 WorkManager/Doze：进程退出、注销、关机或崩溃后，内存中的解析/索引/同步任务即消失。D-26 A 要求两端使用**各自可靠的持久任务机制**，服务端用 PostgreSQL 任务表与 worker，事件只用于状态通知与审计。

架构影响：

1. 解析、OCR、索引、导出、同步重试必须是本地持久任务（任务表 + 状态机 + 幂等键），启动时扫描未完成任务并续跑或标失败（NFR-04、D-26 A）。
2. 状态迁移必须覆盖：排队、执行、取消、失败、重试、完成；卡死任务用 lease 回收（D-26 A）。
3. 应用关闭即退出并提示未完成任务；不做常驻后台服务（课程范围）。
4. 单实例约束：两个实例同时写同一 SQLite 会锁冲突，应使用命名 Mutex 或明确锁策略（【W推断】）。
5. 崩溃恢复只依赖持久状态与日志，不把内存态当可靠状态（D-21 A）。

### 3.5 凭据、令牌与本地敏感数据的安全存储（V1.1 按 D-31 A + 实测修订）

【W实测 + W官方】`TECH-WIN-003` 实测：DPAPI 用户作用域可对当前用户加解密（39 字节明文 → 262 字节密文），密文文件中不含明文的 ASCII/UTF-16 形式；篡改 1 字节或更换熵值时解密失败；同一明文两次加密产生不同密文；**复制密文文件后同一用户仍可解密**；机器作用域本机同样可用；`%APPDATA%\Microsoft\Protect` 为 per-user 主密钥目录。本机同时存在 `cmdkey.exe` 与 `%APPDATA%\Microsoft\Credentials`（未写入）。

架构影响（D-31 A、D-20 A）：

1. 令牌与刷新令牌使用 Windows Credential Manager 或 DPAPI 用户作用域保存，不得进配置文件、日志、崩溃报告与诊断包。
2. 「文件权限与拷贝不是保护边界，用户会话才是」：应用仍需目录权限、日志脱敏、诊断包排除，以及退出登录/设备撤销时的显式删除（AC-08、D-18 A、W-E10）。
3. 共享核心只定义凭据读写契约，Windows 实现与 Android Keystore 是两套平台实现（D-28 A）。
4. 机器作用域会削弱「换用户不可解」，除共享设备需求外应优先用户作用域。
5. 笔记摘录属潜在敏感数据；是否字段级加密由 D-31 A（当前不增加应用层字段加密）与 D-20 A 决定。

### 3.6 Markdown 与 PDF 导出的目标位置与覆盖行为

【W实测 + W官方】`TECH-WIN-001` 测得：普通覆盖写直接替换目标文件，不自动保留旧版本，同目录不产生备份。系统「另存为」对话框通常自带覆盖确认，但确认后仍是直接替换。

架构影响：

1. 导出流程自建：目标选择 → 覆盖确认 → 写入 → 结果反馈 → 失败不静默覆盖（FR-09、AC-20、D-10）。
2. 导出内容必须携带来源版本与引用信息（页码/章节/原文片段），且按 D-25 A 绑定 DocumentVersion；否则跨端导出语义不一致。
3. 导出目录可能位于 OneDrive/网盘同步目录，写入即意味着内容离开本机；提示中必须说明（D-05/D-17 A 边界）。
4. PDF 版式一致性依赖导出库与字体；Markdown 相对可控；二者均需固定样本比对（W-E12）。

## 4 B-D03 Windows 文档能力与引用链分析（V1.1 按 D-22 A 重构）

### 4.1 D-22 A 对 Windows 端的含义

D-22 A 决定：两端分别使用平台原生或成熟文档组件，共享核心只拥有**统一文档能力合同**（页面标识、坐标系、文本范围、能力标记、解析器版本、OCR 来源、降级原因）。`28-D22` 同时明确：桌面 Python 基准可作为能力与金标证据，但**不等于已适合嵌入 Windows 正式客户端**；当前也未选定具体库。

因此本节不再按「共享核心路线」讨论文档引擎，而是按「Windows 组件 → 统一合同字段」盘点。

### 4.2 Windows 候选组件与合同供给能力【V1.1 新增】

| MuPDF | 有 | 有 | 有 | AGPL/商业 | 同上 | 许可与商业授权风险 |
| WinRT `Windows.Data.Pdf` | 有（页面位图） | **无** | 无 | 系统组件 | 仅页面图像与页数 | 不能满足文本、选择与引用合同，只能做预览 |

1. 纯 JVM 的 PDFBox 与原生 PDFium 是 Windows 端最可能满足「页面 + 文本范围 + 坐标」合同的候选；WinRT PDF 只能做预览，不能单独承担引用链。

### 4.3 已观察的解析/OCR 能力（沿用 V1.0 实测）

| 格式 | 已观察结果 | 关键风险 | 证据 |
|---|---|---|---|

### 4.4 阅读顺序、页码与引用锚点

- 引用按 D-25 A 保存**结构锚点 + 字符锚点**并绑定 DocumentVersion；bbox 只用于页面回显，不作为唯一锚点。
- 页码需同时保存「物理页」与「打印页码标签」（NFR-01、AC-06）。
- 目录是派生对象，还原率取决于标题识别；Docling 层级全为 1、脚注召回为 0 说明「目录候选」必须可校验、可降级（AC-04）。
- 页级/块级证据在库层可观察（页码映射率 1.0、bbox 越界检查通过，`TECH-CIT-FOLLOWUP-R01`），但证据契约完整率为 0（缺版本、源哈希、字符偏移，`TECH-RET-007-R01`）；桌面端必须把契约校验放在门控里。

### 4.5 桌面资源预算（按 D-33 B 分级）

【W实测 + W推断】Windows 资源优于 Android 但非无限：索引/OCR 与渲染争抢 CPU 会导致卡顿（NFR-11、NFR-12）。D-33 B 要求按**文本型 / 复杂版式 / 扫描 PDF** 三类分别设预算；10 秒、30 秒、60 秒与 20 份文档只是候选测量点，不是 SLA。Windows 侧已测三类单页「渲染 + 合同生成」耗时（`TECH-WIN-010-R01`：合同 p50 12–22 ms、扫描渲染 p50 116 ms，3 次/样本），但缺内存、批量与双端对照。

### 4.6 渲染组件、抽取组件与共享核心的边界（按 D-28 A）

| 边界 | 建议归属 | 理由 |
|---|---|---|
| 文件选择与路径授权 | Windows 平台适配 | 平台原语，无跨端共性 |
| 页面渲染与选区交互 | Windows 平台适配 | 与 UI/渲染栈强耦合 |
| 低层解析（页/块/bbox/字符偏移） | Windows 平台适配实现，输出统一合同 | D-22 A：组件分端、合同共享 |
| 结构校验、分块、索引、检索、证据契约、引用校验 | 共享核心（KMP） | 业务语义与可测试性（D-28 A） |
| 导出文件写入 | Windows 平台适配 | 目标选择与覆盖行为是平台语义 |

结论：共享核心只承载「文档无关」的合同与规则；任何把 PDF 库类型泄漏进共享核心都会破坏另一端实现（D-22 A、D-28 A）。

## 6 B-D04 Windows 同步与离线场景分析（V1.1 按 D-13 A / D-21 A 修订）

### 6.1 本地数据持有边界

【W推断，D-17 A / D-20 A】本地保留文档本体、全文/向量索引、解析缓存、笔记、进度、同步队列元数据；云端只保存服务端可读的最小结构化同步载荷（D-17 A），不保存文档本体与全文索引（D-05）。Windows 侧：数据在 `%LOCALAPPDATA%` 或用户配置目录，卸载不自动清理，换机/重装需云端重同步；源文件留在原位置，应用只持有路径与身份。

### 6.2 离线修改与同步队列（D-21 A / D-26 A）

【W推断 + 待测】Windows 没有系统级后台调度：离线修改写入本地持久队列，在应用运行期间或下次启动时消费（D-26 A）。

- 同步采用**不可变 SyncOperation** 上传与账号级不透明 cursor 变更流；资源状态、变更记录与幂等结果原子提交（D-21 A）。
- 队列项至少含 `operation_id`、`device_id`、`base_revision`、`item_type`、`payload_hash`，保证重试幂等。
- 应用关闭即停止同步；用户可见状态必须区分「已保存本地」与「已同步云端」（NFR-09、AC-23）。
- 断网、代理故障、VPN 切换表现为超时或证书错误；重试需退避并保留失败原因（D-27 A）。
- cursor 过期时服务端返回 `REBASE_REQUIRED`，客户端重建远端状态并保留未确认本地操作（QA-25）。

### 6.3 路径变化、文件替换与版本不匹配（D-16 A 实测支撑）

| 场景 | 识别手段 | 处理 | 证据 |
|---|---|---|---|
| 同卷移动/改名 | 精确内容哈希相同 | 提示「同一内容已移动」，用户确认后重绑路径 | `TECH-WIN-002` |
| 另一设备/另一路径 | 精确内容哈希 | 匹配则复用文档身份；不匹配则新建版本或独立文档 | D-16 A、W-E02 |
| 同路径内容替换 | 哈希变化 | 新建 `DocumentVersion`，旧索引/引用 stale | `TECH-WIN-002`、BR05 |
| 仅修改时间 | 哈希不变 | **不**新建版本 | `TECH-WIN-002` |
| 换行符/重新导出 | 哈希变化 | 新建版本并提示「内容已变化」 | `TECH-WIN-002` |
| 文件删除/撤权 | 路径不存在或访问被拒 | 停止任务、索引 stale、引用失效 | D-19 A、BR05 |

### 6.4 账号退出、设备撤销、文件撤权与本地残留

【W推断，D-18 A / D-31 A】三类退出必须区分：

1. **账号退出**：删除 DPAPI/Credential Manager 中的令牌条目；本地笔记与索引是否保留由 D-18 A/D-19 A 决定。
2. **设备撤销**：服务端在业务写入前拒绝；客户端进入重新认证，不得继续上传（QA-19）。
3. **文件撤权/删除**：停止对该文档的新检索与模型调用，历史引用标失效（分工方案 2.3 第 6 条、BR05）。

本地残留清理覆盖：解析缓存、OCR 中间图、导出临时文件、日志中的路径与查询。`TECH-WIN-003` 证明密文可被复制且同用户可解，因此「删除令牌文件」必须验证无副本、无日志残留（W-E10）。

### 6.5 同步失败、重复提交、游标失效与冲突副本

【W推断，D-13 A / D-21 A】用户可见状态至少：等待同步、同步中、已同步、失败（可重试）、冲突（保留副本）、游标失效（重新基线）。D-13 A 决定：笔记保留冲突副本、进度取最新有效记录、删除用 tombstone；D-19 A 决定 tombstone 短期保留、期满异步硬删除（天数未定）。

### 6.6 Windows 侧需补的冲突验证场景

| 场景 | 风险 | 归属 |
|---|---|---|
| 关机数天后重连 | 基于 revision 的进度/笔记可能覆盖较新记录 | D-13 A 验证、W-E09 |
| 用户手动改系统时间 | 任何依赖本地时钟的排序失效 | D-21 A 要求服务端序号/游标 |

| 设备撤销后离线仍操作 | 重连被拒后本地操作如何保留 | D-18 A、W-E09 |

## 7 B-05 Windows AI 调用与降级（V1.1 按 D-24 A / D-27 A / D-29 A 修订）

### 7.1 客户端证据选择与最少外发（D-24 A）

客户端在任何外发前完成：文件权限校验、用户同意校验、版本校验、混合检索、重排、去重和证据裁剪；AI/RAG 网关只校验证据包合同、执行长度限制并调用供应方，不主动访问客户端文档（D-24 A）。Windows 侧补充：

1. 逐文件同意在桌面 UI 显式呈现「文件、版本、模型服务、用途、策略版本」，不可复用为永久授权（NFR-08、AC-08）。
2. 同意状态与审计事件本地留痕并同步；退出登录后不得残留「已同意」缓存（D-31 A）。
3. 默认不发送整份文件；只发送通过 Evidence Contract 的最小证据（BR02、BR03、AD-26）。
4. 既有实验 `TECH-ARCH-004` 已证明门控拒绝 4 类用例调用次数为 0；但按 D-29 A，Codex 客户端能力不等同应用 API 证据。

### 7.2 流式响应、取消、超时与轮询回退（D-27 A）

【W推断 + 待测，W-E08】D-27 A 决定 REST/JSON 为主协议、AI 使用 SSE 并提供轮询回退。Windows 特有干扰：

- **系统代理与 TLS 拦截**：企业代理可能缓冲或中断 SSE、注入自签证书；需要可配置代理、错误分类与轮询回退。
- **睡眠/休眠**：合盖后连接中断，恢复时必须把「半条回答」标为失败而非部分成功（NFR-04、QA-32）。
- **取消**：真正中止请求与后续处理，不只隐藏 UI。
- **超时与限流**：30 秒首反馈、1 分钟完成仍是候选目标，未实测前不得写成 SLA（NFR-10、D-33 B）。

### 7.3 模型供应方与降级（D-15 A / D-29 A）

- 一期单一供应方（D-15 A），通过内部 ModelAdapter 隔离；D-29 A 候选为 OpenAI 官方 Responses API 与固定快照 `gpt-5.4-mini-2026-03-17`，须以正式项目账号验证可用性、政策、结构化输出、流式、取消、限流、质量与费用（W-E14）。
- 模型不可用时降级为本地阅读、笔记与本地检索，不生成无据答案（D-06、QA-04、QA-34）。
- 供应方切换需用户显式同意；桌面端要显示当前供应方并记录切换事件。

### 7.4 日志、崩溃报告与诊断（D-32 A）

【W推断，W-E10/W-E11】Windows 崩溃转储（WER）与日志易混入路径、查询、证据片段：

- 结构化日志只记录 ID、状态、错误类别、耗时与重试计数，不记录正文、笔记、证据、令牌、完整路径（D-32 A）。
- 诊断包只在用户主动操作后生成，默认可预览、可裁剪、不上传（D-32 A）。
- 崩溃报告默认不上传；若启用，先脱敏并排除路径与凭据。
- 本地日志保留期与清理规则由 D-31 A/D-32 A 参数决定。

### 7.5 断网/模型不可用时保持阅读、笔记与本地检索

【W实测 + W推断】`TECH-ARCH-003/004` 已验证云端失败回退本地证据与原文；`TECH-RET-*` 证明本地检索链路可运行。Windows 端要求：断网仍能打开已导入文档、阅读、检索已建索引、查看笔记（NFR-09、AC-23）；AI 入口显示明确降级状态；本地生成模型不在一期范围（D-06、FR-12）。

## 10 B-D06 架构建议与验证缺口（V1.1 重写）

### 10.1 与已选方向一致的结论

1. **Windows 端不承担共享核心职责**：KMP 共享领域、同步、合同与测试；Windows 负责 UI、文件、文档组件、数据库、安全存储、后台任务与打包（D-28 A）。
2. **文件身份用精确哈希**：`TECH-WIN-002` 证明该方案在 Windows 上可落地，且时间戳不可作判据（D-16 A）。
3. **凭据用平台安全存储**：`TECH-WIN-003` 证明 DPAPI 用户作用域可用、密文不含明文、篡改可检测；但复制密文仍是风险，需日志与目录边界（D-31 A）。
4. **文档组件分端**：Windows 应选 PDFBox（Apache-2.0，纯 JVM）或 PDFium（BSD-3，原生绑定）之一作为主候选，WinRT PDF 只能做预览（D-22 A，W-E02 待验）。
5. **任务与通信**：客户端持久任务 + REST/SSE/轮询回退（D-26 A、D-27 A），Windows 侧均未验证。

### 10.2 反对或需谨慎的理由

- 不因为「已有 JVM 最小链路」就认为 KMP Windows 目标可行：`TECH-ARCH-001~004` 是单模块 JVM 程序，不是 KMP 多平台 target（W-E01 必须新建）。
- 不因为 DPAPI 可用就认为凭据安全闭环完成：用户切换、重装、日志与诊断包均未验证（W-E10）。
- 不因为库层解析金标通过就认为 D-22 A 已满足：正式组件、坐标精度、选区与回跳未测（W-E02、W-E06）。
- 不因为方向已选就把 ADR 写成 Accepted：D-28/D-29/D-33/D-34/D-35 均有明确关闭门槛（`23-ADR` 第 2 节）。

### 10.3 下一轮 Windows 实验的最小闭环（对齐 W-E）

1. **W-E01**：固定 JDK 21 与 Gradle 版本并建立可复现构建；建 KMP Windows target，消费同一 shared 测试向量；记录构建、依赖图、桥接量（**已完成最小闭环**：`TECH-WIN-004-R01`；下一步是让 Android 目标复跑同一向量）。
2. **W-E02/W-E06**：在 Windows target 内接入 PDFBox（或 PDFium）渲染与文本层，固定 `SELF-001/002/003/004` 做页面/坐标/文本范围/能力/降级对照；再做插页/删页/重排的 stale 样本。
3. **W-E07/W-E09**：本地任务表 + 杀进程/重复领取；接真实最小服务端做重复提交、响应丢失、`REBASE_REQUIRED`。
4. **W-E08/W-E14**：代理/睡眠/SSE 中断与轮询回退；正式 API 证据另立。
5. **W-E10/W-E11**：双用户 DPAPI、日志与诊断包秘密扫描。
6. **W-E12/W-E13/W-E15**：三类文档性能、签名安装升级、干净环境重建。
