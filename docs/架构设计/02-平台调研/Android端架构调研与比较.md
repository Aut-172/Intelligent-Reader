## 3 C-D01 Android 平台架构约束清单

### 3.1 系统文件选择与持久授权（SAF / Content URI）

【A独有】Android 12 及以上不提供类似 Windows 的"固定盘符 + 任意路径"文件模型，应用通过 **Storage Access Framework（SAF）** 以 `ACTION_OPEN_DOCUMENT` 选择文件，得到的是 **Content URI**，而非文件系统路径。与之配套的关键平台事实：

- 授权是**按 URI 授予**的，且默认只对该次会话有效；只有通过 `ACTION_OPEN_DOCUMENT`（隐式或显式 `takePersistableUriPermission`）才能获得**持久读/写授权**。
- 持久授权会**跨设备重启保留**，但会在以下情况失效：提供方应用被卸载、提供方主动撤权、用户清除应用数据（视提供方实现）、或 URI 所指向文档被删除/替换。
- 因此"文档身份"在 Android 端不能只靠路径，必须保存 **DocumentIdentity（指纹/元数据）+ 持久授权 URI + 授权状态** 三元组，并在失效时引导用户**重新选择并重新绑定**（直接呼应 D-05"两端分别重新授权原文件"）。

架构影响：【A独有】本地文件授权必须作为独立职责域存在；读取文件时必须处理 `SecurityException` / 授权失效；文档解析、索引、导出均需适配 Content URI 流式读取而非直接路径。

### 3.2 应用沙箱与存储边界

【A独有】Android 应用运行在**应用沙箱**内，自有数据目录（`/data/data/<pkg>/`）之外的文件访问受 Scoped Storage 约束：

| 数据类别 | 建议位置 | 沙箱/授权影响 |
|---|---|---|
| 解析结果、笔记、进度、索引、同步队列元数据 | 应用内部存储（数据库/文件） | 沙箱私有，随卸载删除；符合本地优先 |
| 源文件 | 用户原始位置（SAF URI 指向） | 不复制进沙箱，保持授权语义 |
| 解析缓存/临时文件 | `cacheDir` / `noBackupFilesDir` | 系统可回收，不得放唯一数据 |
| 导出文件（MD/PDF） | 用户经 `ACTION_CREATE_DOCUMENT` 选定位置 | 写入需用户显式授权，见 3.6 |
| 凭据/令牌 | Android Keystore + EncryptedSharedPreferences | 见 3.5 |

架构影响：【A独有】本地数据必须按"唯一数据 / 可重建缓存 / 敏感凭据"分层；备份机制（Auto Backup）需显式 `dataExtractionRules`/`fullBackupContent` 排除敏感目录，否则卸载/换机可能泄漏或误恢复（D-20 相关输入）。

### 3.3 交互与窗口约束

【A独有】触摸优先、小屏、手势缩放、文本长按选区、系统返回手势、横竖屏与多窗口分屏：

- 阅读交互（选择、划词、bbox 回跳）必须适配**触控精度**，Windows 的鼠标 hover/拖拽语义不能直接照搬。
- 系统返回键/手势会触发 `onBackPressed`，旋转或分屏会触发 Activity 重建，长任务不能依赖 Activity 存活。
- 文档渲染与文本选择组件需处理**系统选区手柄**（selection handles）与自定义 bbox 命中的协同，避免二者互相冲突。

### 3.4 生命周期、进程回收与后台限制

【A独有】Android 会因内存压力、系统进入 Doze/App Standby、或后台执行限制而**随时回收进程**；不能假设任何后台长任务默认存活：

- 解析、OCR、索引、导出等长任务必须用 **WorkManager（持久任务）或前台服务（Foreground Service + 通知）**，并设计幂等与断点续跑，不能放在 Activity 内。
- 前台服务受通知可见性约束；后台执行受电量/配额限制，弱网与大文件场景必须可取消、可重试。
- 锁屏、网络切换、进程被杀后恢复，直接影响同步游标与任务状态（详见第 6 章）。

### 3.5 安全存储与凭据

【A独有】账号令牌、设备标识、本地敏感数据必须使用 **Android Keystore**（硬件级密钥，不可导出）配合 **EncryptedSharedPreferences / 密钥库加密**；纯 `SharedPreferences` 或明文数据库不可用于凭据。设备标识应使用去标识化的自生成实例 ID 而非硬件 IMEI（IMEI 需权限且受隐私限制）。

架构影响：【A独有】安全存储是独立平台适配点，共享核心只能定义"凭据读写契约"，不能假设密钥来源；Windows 的凭据安全存储（如 Windows Credential Manager）与 Android Keystore 是**两个不同适配实现**。

### 3.6 Markdown 与 PDF 导出

【A独有】导出必须通过 `ACTION_CREATE_DOCUMENT` 让用户显式选择目标位置，应用获得对该新文件的写授权；与"打开源文件"的授权是两套流程。覆盖行为、失败恢复、导出时写入来源版本与引用信息（D-10）需在 Android 侧单独验证，不能复用 Windows 的路径式覆盖语义。

### 3.7 平台约束汇总表

| # | 平台约束 | 架构影响 | 证据等级 |
|---|---|---|---|
| 1 | SAF + Content URI + 持久授权 | 引入文件授权职责域，处理授权失效/重新绑定 | 【A独有】 |
| 2 | 应用沙箱 + Scoped Storage | 本地数据分层，缓存与唯一数据分离 | 【A独有】 |
| 3 | 触摸/小屏/返回手势/重建 | 阅读交互与选区组件平台适配 | 【A独有】 |
| 4 | 进程回收 + Doze/后台限制 | 长任务持久化、幂等、可恢复 | 【A独有】 |
| 5 | Keystore + 加密存储 | 安全存储平台适配，设备标识去标识化 | 【A独有】 |
| 6 | ACTION_CREATE_DOCUMENT 导出 | 导出授权与覆盖语义单独设计 | 【A独有】 |
| 7 | 最低 Android 12 / API 31 | 所有 SDK、依赖、权限声明以 API 31 为下限 | 【官方】 |
| 8 | release APK 侧载 | 签名、升级、卸载与 ABI 验证计划 | 【官方】 |

## 4 C-D03 Android 文档能力与引用链分析

### 4.1 文档渲染与解析路线

一期格式为 PDF、DOCX、Markdown 与扫描文档（OCR），按 D-22 属 Research Question，本文档只做 Android 端能力盘点：

| 格式 | Android 端候选能力 | 关键风险 | 证据等级 |
|---|---|---|---|
| PDF | 平台原生 `PdfRenderer`（渲染页位图）能力有限，**无内置文本抽取/选择**；第三方引擎（如 Pdfium/PDFBox 移植、商用 SDK）可提供文本、bbox、选择 | 原生能力上限低，第三方需桥接进共享核心；渲染结果与抽取的坐标体系易不一致（SELF-001 已实测一致，见 TECH-ANDROID-003-R01） | 【官方】/【A实测】 |
| DOCX | 无系统原生解析；需第三方解析库或走共享核心 | 复杂版式、表格、脚注归一化在移动内存受限下更敏感 | 【待测】 |
| Markdown | 纯文本可共享核心处理，渲染需平台 UI 组件 | 风险低，主要验证渲染样式一致性 | 【W共享】 |
| 扫描件 OCR | Android 无强官方 OCR 路径；需第三方（端侧 ML Kit / 离线引擎）或受控在线服务 | 内存/CPU/功耗预算、是否触发 OCR 的判定阈值 | 【待测】/【依赖D】 |

### 4.2 文本选择、搜索、目录、页码、bbox 与引用回跳

【A独有】Android 文本选择由系统选区 + 文档组件协同实现，与 Windows 的鼠标划词语义不同；bbox 回跳依赖文档组件提供稳定的坐标与阅读顺序。核心风险是：

- 不同文档组件产生的文本块、坐标、阅读顺序**不可直接互换**，若渲染组件与抽取组件分离，需维护统一的文本块/锚点契约（D-25 输入）。
- 移动端长文档分页、缩放后 bbox 需做坐标变换；引用锚点建议用"字符范围 + 结构锚点"双锚点并加文本校验，避免单 bbox 失效。
- 这些已在 Android 固定样本 SELF-001 上实测：PdfBox-Android 产出字符级 bbox+页码+锚点命中+阅读顺序（TECH-ANDROID-003-R01）。Windows 渲染结论只提供"共享锚点契约语义"（【W共享】）；Android 组件已能产生同样锚点（【A实测】(SELF-001)），多栏/表格/扫描件仍需继续验证。

### 4.3 移动资源预算

【A独有】移动设备内存、CPU、存储、功耗约束显著严于 Windows，直接影响：

- 解析、OCR、索引是否可在设备端完成，以及 20 份文档候选上限（D-23）在低端 Android 12 设备上的内存/磁盘/索引时间是否可行。
- 大文件解析需流式/分页处理，避免一次性载入整文件导致 OOM。
- 后台索引/OCR 受 Doze 限制，需电量预算与可取消设计。
- 以上均需真机 + 固定样本测量，不能用 Windows 性能数字外推（【待测】）。

### 4.4 平台原生 vs 第三方组件 vs 共享核心桥接的边界

- 平台原生 PDF 能力（`PdfRenderer`）只适合"渲染预览"，不足以支撑选择、搜索、bbox 回跳的完整证据链，因此**一期 PDF 证据链大概率依赖第三方文档引擎或共享核心桥接**（【待测】）。
- 文档能力应尽量收敛到"共享核心文档契约 + 平台文档适配器"两层，避免 Android 与 Windows 各维护一套互不兼容的文本块/锚点语义（【W共享】）。

### 4.5 文档能力汇总表

| 能力 | Android 现状判断 | 证据等级 |
|---|---|---|
| PDF 渲染 | 原生可渲染位图，能力上限低 | 【官方】 |
| PDF 文本抽取/选择/bbox | 需第三方引擎或共享核心；PdfBox-Android 在 SELF-001 实测产出文本块+bbox+阅读顺序（TECH-ANDROID-003-R01） | 【A实测】 |
| DOCX 解析 | 无原生，依赖第三方/共享核心 | 【待测】 |
| Markdown | 共享核心可处理，风险低 | 【W共享】 |
| OCR | 无强官方路径，需端侧或受控在线，阈值待定 | 【待测】/【依赖D】 |
| 引用锚点与回跳 | 字符级 bbox+页码+锚点命中在 SELF-001 实测（TECH-ANDROID-003-R01）；完整双锚点契约仍待 D-25 | 【A实测】(SELF-001) |

## 5 C-D02 Android 候选路线比较矩阵

### 5.1 前提

按 D-03，共享核心只覆盖领域模型、业务规则、数据契约与可测试核心，UI 与平台适配**分别实现**。因此本矩阵比较的是"共享核心 + Android 平台实现"的组合，不把共享 UI 复用率作为首要目标。D-12 仅决定下一轮实验覆盖范围，本矩阵不宣布最终技术栈。

### 5.2 三条候选路线

- **路线 A：KMP 共享核心 + Android Kotlin/Compose 平台实现**。共享核心用 Kotlin Multiplatform（common 代码），Android 端天然运行于 JVM/Kotlin，桥接成本最低。
- **路线 B：共享 Rust 核心 + 稳定桥接 + Android 原生 UI**。共享核心用 Rust（解析/索引等性能敏感逻辑），经 UniFFI/JNI 桥接到 Kotlin，UI 仍用原生 Kotlin/Compose。
- **路线 C：Qt for Android（对照）**。C++/QML 全栈，Qt PDF 可作为文档渲染能力上限对照；若大量共享 QML UI 则偏离 D-03，仅作为平台组件或能力对照。

### 5.3 统一比较矩阵（12 维度 × 3 路线）

| 维度（A-04） | A：KMP + Kotlin/Compose | B：共享 Rust + 桥接 + 原生 UI | C：Qt for Android（对照） |
|---|---|---|---|
| 1 平台正式支持 | 高；Kotlin/JVM 是 Android 一等公民，KMP 被官方工具链支持【官方】 | 中高；需 NDK + FFI，非官方默认路径【官方】 | 中；Qt 官方支持 Android 但非 Android 主流【官方】 |
| 2 文档与复杂版面 | 依赖第三方 Android 文档组件/共享核心适配【待测】 | Rust 侧性能强，但仍需 Android 文档组件产出 bbox【待测】 | Qt PDF 能力较强，可作能力上限对照【官方】 |
| 3 文件选择与授权 | 标准 SAF 集成，桥接成本低【A独有】 | SAF 在 Kotlin 侧处理，Rust 核心不感知 URI【A独有】 | QML 侧集成 SAF，需 JNI 桥接【待测】 |
| 4 选择/搜索/bbox/回跳 | 依赖 Android 文档组件 + Compose 选区【待测】 | 同左，回跳契约由共享核心定义【待测】 | Qt 渲染与 QML 交互一体化，但偏离分端 UI【依赖D】 |
| 5 本地数据/索引/安全存储 | Room/SQLDelight + Keystore 生态成熟【官方】 | Rust 索引引擎 + Kotlin 侧安全存储，双层维护【待测】 | Qt SQLite + 需自行桥接 Keystore【待测】 |
| 6 后台任务/进程恢复 | WorkManager/前台服务标准方案【A独有】 | 长任务在 Rust 侧需处理生命周期中断边界【待测】 | Qt 后台与 Doze 集成成本高【待测】 |
| 7 共享核心接入/桥接成本 | 最低；同语言同运行时，无 FFI【官方】 | 高；UniFFI/JNI + ABI 管理 + 序列化边界【官方】 | 高；C++/JNI + QML 桥接 + 工具链【官方】 |
| 8 release 构建/签名/侧载/升级 | 标准 AGP 流程，成熟【官方】 | NDK + 多 ABI 构建，包体/签名需额外配置【官方】 | Qt 工具链 + 部署，APK 体积显著更大【官方】 |
| 9 性能/内存/磁盘/开发环境 | JVM 可接受，开发环境轻【官方】 | 解析/索引性能上限高，编译/调试链重【官方】 | APK 体积、内存与学习成本高【官方】 |
| 10 测试/调试/日志 | Kotlin 生态成熟，单测/仪器测试丰富【官方】 | Rust 单测 + FFI 边界测试，调试链路较陡【官方】 | C++ 调试与 CI 成本高【官方】 |
| 11 许可证/第三方依赖 | Apache-2.0 生态，风险低【官方】 | Rust crates 生态，需逐个审核【官方】 | LGPL v3 / 商业许可，分发合规成本高【官方】 |
| 12 课程周期/团队技能/剩余验证 | 技能匹配度最高，验证成本最低【待测】 | 需 Rust + NDK 技能，验证成本高【待测】 | 需 C++/QML 技能，成本最高【待测】 |

### 5.4 结论与证据等级

- 三条路线均"可行但未在 Android 端实测"，正式结论须以 D-12 获批实验为准。
- 就"共享核心 + 分端 UI"这一 D-03 目标而言，**路线 A 的桥接与工具链成本最低，路线 B 在解析/索引性能上有上限优势，路线 C 更适合作为文档能力对照而非共享核心路线**。
- 上述倾向是【官方】层面的架构推断，**不能替代 Android 最小工程验证**；若 D-12 选择 A，还需验证 Android 文件 URI、后台任务、文档组件与 release 构建这四类此前 Windows 实验未覆盖的缺口。

## 6 C-D04 Android 同步与离线场景分析

### 6.1 本地数据持有边界

【W共享】本地优先语义与 Windows 一致：文档本体、全文索引、解析缓存、笔记、进度、同步队列元数据均保留在设备本地；云端只同步最小身份、进度、笔记、文档身份与版本元数据（D-05、D-17）。Android 特有之处是**本地数据落在应用沙箱内，随卸载丢失**，需在账号退出/换机/重装时提供云端重同步路径。

### 6.2 离线修改进入同步队列与重试

【A独有】Android 网络状态切换频繁（Wi-Fi/移动网络/弱网/无网），同步队列需：

- 本地离线修改先落本地持久队列（含 operation id、device id、base revision），网络恢复后按游标增量上传。
- 重试需指数退避 + 幂等键；进程被杀后由 WorkManager 恢复队列消费，不能依赖内存态游标。
- 上传与拉取需处理"部分成功"，失败项不阻塞后续项（D-21 输入）。

### 6.3 进程回收、重启对游标与任务状态的影响

【A独有】这是 Android 区别于 Windows 的最大风险点之一：Windows 桌面进程关闭/重启相对可控，Android 的进程回收更随机。要求：

- 同步游标、任务状态机、操作队列全部**持久化**，任何时刻进程被杀后能从持久状态恢复，不得产生重复或丢失。
- 解析/索引/导出/同步任务以 WorkManager（唯一/链式）建模，幂等 + 断点续跑；任务卡死或状态倒退需有恢复与审计（D-26 输入）。

### 6.4 账号退出、设备丢失、令牌撤销与本地清理

【A独有】需区分"设备撤销"与"本地清理"：

- 账号退出/设备撤销后，本地敏感数据（令牌、索引、摘录缓存）需清理；但普通笔记/进度是否保留需按 D-18/D-19 语义决定（【依赖D】）。
- 令牌撤销后离线设备重连会被服务端拒绝，客户端需进入"重新登录/重新授权"状态，不得继续上传。
- 设备丢失场景依赖服务端设备撤销 + 令牌轮换（D-18 输入），本地侧需保证退出后无残留令牌。

### 6.5 stale 与重新绑定

【A独有】Android 端文件授权失效（提供方卸载、文档删除/替换、版本变化）会导致"源文件无法重新授权"：

- 需用 DocumentIdentity 与 DocumentVersion 识别版本不匹配（D-16 输入）；无法匹配时保持独立文档或引导用户显式绑定。
- 版本变化/撤权后，新的检索与模型使用必须被阻断，历史引用支持失效标记（2.3 第 6 条），Android 侧需在授权失效时停止活动任务并清理残留。

### 6.6 D-13 决策输入（冲突策略的 Android 侧影响）

| D-13 候选 | Android 侧影响 | 证据等级 |
|---|---|---|
| A 笔记保留冲突副本 + 进度最新有效 + tombstone | 需冲突 UI（列表/副本查看/手动合并），适合个人低并发；Android 触摸交互下冲突操作成本可控 | 【待测】 |
| B 字段级合并/CRDT | 富文本、引用锚点、重排语义复杂，移动端实现与测试成本高 | 【待测】 |
| C 全部 LWW | 实现最简，但离线设备静默覆盖重要笔记风险高，需时钟偏差/断网重连实验评估 | 【待测】 |

> C 的建议倾向：从"个人、低并发、可解释、不静默丢笔记"出发，倾向 A，但需 Android 端离线并发 + 删除/编辑竞争 + 时钟偏差实验验证后，再由 A 汇总（最终由项目负责人批准，本文档不宣布结论）。

## 7 C-05 Android AI 调用与降级

### 7.1 逐文件同意、最少证据外发、流式与取消

【W共享】逐文件同意、权限过滤、最少证据选择、流式响应、取消与超时的**语义**与 Windows 一致，但 Android 侧交互边界不同（【A独有】）：

- 用户同意需绑定到具体供应方/模型类别（D-15 研究问题），Android 端需在触摸界面显式确认后放行外发。
- 流式响应建议用 SSE/WebSocket，但移动网络与代理对流式协议支持需单独验证（D-27 输入）。
- 取消需真正停止外发与本地任务，不能只隐藏 UI。

### 7.2 弱网、网络切换、前后台与系统回收

【A独有】移动网络切换、弱网、断网、前后台切换与系统回收都会中断或干扰 AI 调用：

- 请求需幂等 + 超时 + 退避；网络切换导致连接中断时不能重复外发证据。
- 系统回收后台 Activity/Service 时，进行中的流式响应需能安全中止并标记失败，避免"半条回答"进入状态。
- 供应方故障/限流时需可解释降级，用户可见原因。

### 7.3 降级与本地能力保持

【W共享 + A独有】D-06 要求无端侧生成模型时仍保持离线阅读与本地检索：

- 断网/模型不可用时，Android 端必须能继续**本地阅读、笔记、已建索引检索**，并返回"仅本地检索结果"而非报错。
- 在线生成只是增强路径，其可用性不影响核心本地能力（2.3 第 5、6 条）。

### 7.4 隐私字段控制（日志、崩溃、遥测）

【A独有】移动端日志/崩溃/遥测易混入原文、查询、证据、密钥与未授权路径：

- 需结构化字段 + 去标识化 + 脱敏；崩溃报告（如 Crashlytics）不得携带文档内容、查询或证据。
- 外部调用日志不得记录原文、密钥与未经授权路径（与 B-05 同语义【W共享】）。

### 7.5 D-15 决策输入

- 单一供应方（A）：Android 侧验证面最小，需验证超时/限流/取消/替换桩（【待测】）。
- 主备供应方（B）：切换需用户显式同意，Android 侧需处理"自动回退是否超出本次同意"的交互（【待测】）。
- 自托管/校内端点（C）：与 Android 端关系主要是网络可达性与时延，需真实双端访问验证（【依赖D】）。

## 8 C-D05 Android release 验证计划

### 8.1 最低版本、目标 SDK 与权限声明

【官方】以 Android 12（API 31）为 `minSdkVersion` 下限，`targetSdkVersion` 取当时 Google Play 要求的现行版本（不依赖 Play 分发，但需满足侧载场景的行为预期）。权限声明只保留一期必需项（如存储相关 SAF 不需要旧式存储权限、网络、前台服务），并逐一说明用途与运行时授权时机（D-07、D-08）。

### 8.2 release APK 签名、侧载、首次启动、升级覆盖、卸载

【官方】D-08 要求侧载 release APK，验证项：

- release 用正式签名（可自签名 keystore）构建，验证 `minifyEnabled`/R8 后无缺类/资源问题。
- 侧载安装：验证"未知来源"安装流程、签名一致性、首次启动冷启动与权限弹窗顺序。
- 升级覆盖：验证同签名高版本覆盖安装时本地数据库迁移、持久授权 URI 与同步游标保留。
- 卸载：验证卸载后无残留文件/密钥/外部痕迹（配合 D-20）。

### 8.3 ABI、包体、原生依赖与共享运行时

【官方】若引入 NDK/Rust（路线 B）或 Qt（路线 C），需为 `arm64-v8a`（及必要的 `armeabi-v7a`）分别构建并核对 ABI 兼容；记录 APK 体积、原生依赖与共享运行时（如 Qt 库）对包体的影响。纯 KMP 路线（A）无 NDK 依赖，包体风险最低。

### 8.4 真机与模拟器验证边界

【A独有】D-08/分工方案明确"避免只凭模拟器得出发布结论"：

- 安装、升级、卸载、持久授权、SAF 与第三方文件提供方（如系统文件管理器、云盘 Provider）行为必须在**真机**验证。
- 模拟器仅用于逻辑回归与 CI 快速反馈，不作为发布结论依据。
- 至少覆盖 Android 12（API 31）真机一台 + 更高版本一台做兼容对照。

### 8.5 固定样本回归、性能测量、崩溃日志、依赖升级

【W共享 + A独有】与 Windows 一致的验证方法论（固定样本、性能统计口径、依赖升级回归），但必须在 Android 真机上重新测量，且分别报告 Android 与 Windows 结果，不能混用（D-33）。

## 10 C-D06 架构建议与验证缺口

### 10.1 推荐倾向与适用条件

- **共享核心路线**：在不宣布最终技术栈的前提下，Android 端证据目前更支持 **路线 A（KMP 共享核心 + Kotlin/Compose 平台实现）** 作为下一轮最小工程验证的首选对象——因为它对 D-03"分端 UI + 共享核心"目标桥接成本最低、工具链最成熟、团队技能最匹配。该倾向适用于 D-12 选择"只补齐 KMP Android 最小工程"（A）或"KMP 与其他对照并行"（B/C）时的基线工程。
- **适用条件**：路线 A 的前提是"文档能力由 Android 文档组件适配层承担、共享核心只承载文档无关的领域/同步/契约语义"；若一期强烈依赖单一跨端文档引擎，则需评估 Rust/Qt 文档引擎的桥接收益（需 D-12 实验数据）。

### 10.2 反对理由与风险

- 路线 A 的主要风险是 **Android 文档组件（PDF/DOCX/OCR）的 bbox 与引用链一致性未经实测**，可能需要在平台适配层投入比预期更多的工作；KMP 共享核心本身不解决文档能力。
- 路线 B 的 Rust 解析/索引性能优势**尚属推断**，若 Android 一期文档量（20 份候选上限）与本地索引需求未到性能瓶颈，Rust 的桥接与调试成本可能不划算。
- 路线 C（Qt）会引入 LGPL/商业许可、APK 体积与 C++/QML 工具链，且共享 QML UI 偏离 D-03，**不建议作为共享核心主线**，仅保留其 PDF 能力作为文档能力上限对照。

### 10.3 最小工程验证计划（下一轮 Android 实验）

目标：用最小工程补齐 Windows 实验未覆盖的 Android 平台事实，而非直接实现产品。建议至少覆盖：

> 落地状态：最小验证工程已建于 `experiments/android-minimal/`（`shared` 纯 Kotlin 共享核心 + `app` Android 平台适配，6 项待测实验 + JVM 单元测试 + 仪器测试），验证计划与证据索引见 `05-验证计划与证据索引/Android端验证计划与证据索引.md`；实测结果按该索引回填为【A实测】。

1. **文件授权最小实验**：SAF 打开 + `takePersistableUriPermission` + 重启后读 + 授权失效（卸载提供方/删除文件）→ 重新绑定的最小闭环。
2. **后台任务最小实验**：WorkManager 执行解析/索引任务 + 进程被杀 + 断点续跑 + 幂等。
3. **文档组件探针**：候选 PDF 组件在固定复杂样本上的文本抽取、bbox、阅读顺序、选择命中与引用回跳的度量（金标比对）。
4. **同步最小实验**：离线修改入队 → 网络恢复重试 → 游标持久化 → 进程回收恢复，验证无重复/丢失。
5. **release 最小实验**：自签名 release APK 侧载、升级覆盖、卸载残留、arm64 ABI + 包体记录。
6. **AI 降级最小实验**：断网/供应方故障/取消下的本地检索可用性与流式中止行为。

每个实验需登记：样本、设备、Android 版本、计量口径、停止条件（对应 D-12 研究问题 4）。
